# 배경

이전 프로젝트에 대해 여기 적힌 원인과 교훈은 그때 그렇게 판단한 기록이고, 검증된 것이 아니다. 사실만 참고하고 결론은 이 프로젝트에서 다시 따진다 ([CLAUDE.md](../CLAUDE.md)).

## 이전 프로젝트

- 저장소: https://github.com/zzingobomi/horibot. 레포 이름은 이 로봇(호리봇)과 같지만 다른 프로젝트이고, 이어가지 않는다. 하드웨어와 캘리브레이션 기록은 참고한다 (`docs/hardware.md`, `docs/calibration.md`).
- 로봇 두 대를 썼다. 둘 다 이제 쓰지 않으며, 분해해서 모터를 옮겨 쓸 수 있다.
  - **SO-101 6DOF**: SO-101에 ts_flake wrist yaw 개조로 1축을 더한 팔. Feetech 서보 7개.
  - **OMX_F**: ROBOTIS 5축과 그리퍼. Dynamixel 6개.

## SO-101 6DOF의 기구학 문제

URDF(`robot/so101_6dof/urdf/so101_6dof.urdf`)를 영점 자세에서 풀어 본 값:

| 구간 | 길이 |
|---|---|
| 위팔 (J2 → J3) | 116 mm |
| 아래팔 (J3 → J4) | 135 mm |
| 손목과 그리퍼 (J4 → TCP) | 약 195 mm |

- **손목이 팔보다 길다.** 손목/팔 비가 약 0.78이다 (UR5는 대략 0.2). TCP를 한 점에 두고 자세만 바꿀 여유가 거의 없다. 대략 계산하면 모든 방향 자세가 나오는 위치는 어깨에서 6 cm 안쪽뿐이다. 실제로 써 봐도 손목이 길어 6축으로 쓰기 불리했다.
- **손목 세 축이 한 점에서 만나지 않는다.** J5와 J6 축은 만나지만 J4 축이 29 mm 비켜 있다.
- **특이점이 범위 끝에 붙어 있다.** J5 = ±90°에서 J4와 J6 축이 나란해지는데, J5 한계가 ±87°다.
- **관절 범위가 좁다.** J1 ±90°, J6 0~180°.
- **CAD에서 뽑은 URDF라 오차가 섞여 있다.** 예: J5 원점에 0.51° 기울기.
- **사양표와 실물이 달랐다.** 어깨에 넣은 STS3250은 문서상 STS3215와 외형이 같다고 돼 있었지만(45.2 × 24.7 × 35 mm), 실제로 SO-101 부품에 넣을 때 잘 들어가지 않았다. 눈으로는 맞아 보였지만 벽을 갈아 내고 억지로 끼워야 했고, 그래서 다시 빼기도 어렵다. 원인이 서보 크기인지 출력물 치수인지는 확인하지 않았다.

## 정밀도 문제

이전 프로젝트의 `docs/calibration.md`와 `docs/hardware.md` 요약.

- hand-eye σ가 SO-101+D405에서 0.80° / 7.53 mm, OMX에서 0.65° / 7.94 mm(처짐 모델까지 적용)에서 더 내려가지 않았다. 보정 없는 값은 3.45° / 24.9 mm(OMX)였다.
- 알고리즘으로는 더 내릴 수 없었고, 하드웨어가 한계였다. 캘리브레이션에 많은 시간이 들었다.
- 원인:
  1. **서보 백래시**: STS3215 실측 ±0.87°.
  2. **중력 처짐**: 자세마다 다르다. 팔을 폈을 때 어깨 정적 토크가 27~30 kg·cm로 STS3215의 최대 토크(30 kg·cm, 스톨 기준)와 같은 수준이라, 어깨만 STS3250으로 바꿨다.
  3. **URDF와 실물 불일치**: 링크 오프셋 보정값이 최대 29 mm까지 나왔다 (처짐 모델을 넣기 전, 다른 오차까지 흡수한 값).
  4. **관절 영점**: J3 +6.6°, J5 −5.3° 같은 보정값이 영점 문제인지 링크 문제인지 BA로 가려낼 수 없었다.
  5. **측정 쪽**: 종이 ChArUco 보드의 평탄도, D405 intrinsic.
  6. **전원 전압**: OMX_F는 11V 전원으로 돌렸는데, XL430이 정격 전압 하한 근처라 자세에 따라 처지는 문제가 있었다.
- 교훈: **정밀도는 캘리브레이션이 아니라 설계 단계에서 잡는다.**

## 이전 프로젝트의 연결 구조

이전 프로젝트의 `docs/hardware.md`, `CLAUDE.md`와 커밋 기록 요약.

- Windows PC 1대와 라즈베리파이 3대를 같은 네트워크(Zenoh)로 묶었다. 파이가 로봇 제어 루프를 직접 돌리고, PC는 계획과 인식 같은 상위 판단을 했다.
  - pi_hori1: SO-101 서보 (Waveshare 어댑터, USB)
  - pi_hori2: SO-101 손목의 D405
  - pi_hori3: OMX_F 서보 (OpenRB-150)와 UVC 카메라
- 처음에는 PC에 직접 연결했다. 2026-05-10에 OMX_F를 PC에 물린 상태에서 실시간 포인트 클라우드를 켜자 모터 6개의 위치 읽기가 모두 실패했고("There is no status packet"), 끄면 정상이었다. D405를 PC 뒷면 포트에 꽂으면 마우스가 먹통이 됐다.
- 다음 날 카메라와 모터를 다른 파이로 나눴다. 기록된 이유는 "D405와 모터 컨트롤러가 한 USB 컨트롤러를 공유하지 않게"다. 원인을 측정한 기록은 없다. 당시 모든 기능이 Python 프로세스 하나에서 돌았으므로, 계산 부하가 모터 통신을 밀어냈을 가능성도 있다.
- 파이마다 SSH로 들어가 코드를 받고 실행해야 해서 배포가 번거로웠다.
- PC에서 테스트나 시뮬레이션을 돌리면 같은 네트워크의 실제 모터가 움직일 수 있어서 격리가 필요했다.

이 교훈을 반영한 새 연결 구조는 [0025](decisions/0025-controller-on-pi.md)에 있다.

## 사지 않고 만드는 이유

- 100만 원대 6축은 myCobot 280 급이다. $650~900, 도달 거리 280 mm, 가반하중 250 g, 반복 정밀도는 ±0.5 mm로 표기돼 있지만 리뷰를 보면 절대 정확도가 나쁘다. 서보 기반이라 같은 종류의 문제가 남는다.
- 정밀도가 확실히 좋아지는 BLDC+감속기 팔은 수백만 원대라 예산 밖이다.
- 출발점이 3D 프린터로 로봇을 직접 만드는 것이다.
