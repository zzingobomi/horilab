# 0025. 컨트롤러는 로봇 옆 파이에: PC 없이도 쓰는 로봇

- 상태: 채택
- 날짜: 2026-11-10

## 배경

- [0023](0023-robot-controller.md)은 응용과 상관없는 로봇 컨트롤러(이동 명령 API, 블렌드, 안전, 펜던트)를 제안했다. 그 "정할 것" 5번이 컨트롤러를 어디서 계속 돌릴지다.
- 컨트롤러는 한 곳에 있어야 한다. 켜진 PC를 따라 옮겨 다니면 조종권이 둘로 갈라지고, 로봇 설정(영점, 서보 설정)을 두 곳에서 맞춰야 하고, 같은 명령이 다르게 움직일 수 있다. 그래서 먼저 목표를 정해야 했다: 개발 PC 없이도 로봇을 쓰는가.
- [0005](0005-connection-architecture.md)는 서보를 PC에 직접 꽂았다. 자주 고치는 코드가 PC에서 바로 돌게 하려는 것이었다. PC 부하가 모터 루프를 밀어낼 수 있다는 걱정은 남아서, 그때는 모터 제어를 파이로 옮긴다고 적어 두었다 (0005의 영향, [0009](0009-control-architecture.md)).
- 가진 파이는 라즈베리파이 4B 4GB 세 대다 ([hardware.md](../hardware.md#가진-것)). 4코어 Cortex-A72(1.5 GHz)라 코어 하나가 데스크톱보다 몇 배 느리고, USB 포트 넷이 USB 컨트롤러 하나를 같이 쓴다.
- 이전 프로젝트도 파이가 제어 루프를 돌리고 PC가 계획과 인식을 했다 ([background.md](../background.md#이전-프로젝트의-연결-구조)). 기록된 사실: 파이마다 SSH로 들어가 코드를 받고 실행해서 배포가 번거로웠다. 카메라와 서보를 다른 파이로 나눴다. 20 ms 목표의 궤적 주기가 최악 32.8 ms까지 기록돼 있다 (이전 프로젝트의 `backend/logs`, 원인은 모름).

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. PC가 켜져 있을 때만 쓴다. 컨트롤러는 개발 PC, 파이는 카메라만 | 가장 단순하다. 고친 코드가 바로 실물로 돈다 | PC가 잠들거나 바쁘면(비전, GPU 작업, 업데이트) 로봇이 영향을 받는다. 0023의 "응용과 상관없는 컨트롤러"가 개발 PC의 프로그램 하나가 된다. PC 없이 보여 주거나 조작할 수 없다 |
| B. PC 없이도 쓴다. 컨트롤러는 로봇 옆 파이에 있고, PC는 켜져 있을 때 붙는 손님이다 | PC 부하가 모터 루프에 닿지 않는다. 산업용처럼 컨트롤러가 로봇 옆에 있다. PC 없이 폰·게임패드로 조그와 티칭, 가르친 동작 재생을 할 수 있다. 파이가 이미 있다 | 실물 시험에 파이 배포가 끼어서 배포 명령이 필요하다. PC에서 쓸 시뮬레이션 컨트롤러를 따로 마련해야 한다. PC 없이 쓰려면 경로 계획도 파이에서 돌아야 한다 |

컨트롤러(0009의 실행 루프와 안전 검사가 있는 프로그램)의 언어는 컨트롤러가 도는 곳이 정한다.

| 언어 | 판단 |
|---|---|
| Python | 개발 PC에서 돈다면 낫다. Windows 자체가 주기 흔들림을 만들어 Rust의 이점이 줄고, 100 Hz면 Python도 여유가 있다(추정). 시뮬레이션을 같은 코어에 붙이기 쉽고, IK·MuJoCo·테스트와 한 언어다 |
| Rust | 파이에서 돈다면 낫다. 파이 CPU가 느려 Python의 처리 몫과 흔들림이 커진다. Rust는 쓰레기 수집이 없고, 리눅스 실시간 커널의 이점을 온전히 쓰고, 실행 파일 하나로 배포된다. 오류를 값으로 다뤄서 처리 누락을 컴파일러가 잡는다. 같은 프로토콜 코드를 나중의 마이크로컨트롤러와 나눌 수 있다 |

## 결정

B로 한다. 컨트롤러는 Rust로 짠다.

- 연결: 서보 어댑터는 로봇 옆 컨트롤러 파이에, D405는 다른 파이(카메라 파이)에 꽂는다. USB 컨트롤러를 나누려는 것이다. PC와 두 파이는 유선 랜으로 잇는다. 세 번째 파이는 여분이다. 이 기록이 0005를 대체한다 (D405를 파이에 꽂아 영상을 랜으로 보내는 부분은 그대로다).
- 개발할 때는 어댑터를 PC에 꽂고 같은 컨트롤러를 PC에서 돌려도 된다. 관절 하나 시험이 그렇다. 어댑터는 한 번에 한 기계에만 꽂히므로 컨트롤러가 둘이 되지 않는다.
- PC에서는 같은 컨트롤러를 시뮬레이션 백엔드로 돌린다 (UR의 URSim처럼). 경로 계획과 응용은 상대가 시뮬레이션인지 실물인지 모른다 (0009 그대로).
- 언어: 컨트롤러(서보 프로토콜, 관절 변환, 안전 검사, 실행 루프, 실물 기록, 서보 준비와 관절 시험 명령)는 Rust다. 공식 서보 SDK는 Python과 C++뿐이라 서보 프로토콜도 Rust로 직접 짠다 ([0024](0024-servo-bus.md)에서 파악한 세부와 SDK의 결함을 바탕으로). 설계, 경로 계획(IK), 시뮬레이션 물리, 비전, 분석, 도구는 Python 그대로다.
- 세 단계로 나눠 만든다. 제작 로드맵의 번호와 섞이지 않게 다른 곳에서는 번호 대신 이름으로 부른다.
  1. 관절 하나 시험: Rust 컨트롤러의 기본(서보 버스, 서보 준비, 버티며 기록)을 0024의 순서로 만들고 PC에서 돌린다.
  2. 팔 움직이기: 컨트롤러를 컨트롤러 파이에 올리고, PC의 경로 계획이 궤적을 네트워크로 보낸다. 파이 배포 명령과 PC 시뮬레이션 컨트롤러를 만든다.
  3. PC 없이 쓰기: 경로 계획을 파이로 옮긴다. 펜던트 화면은 컨트롤러가 직접 열어서 처음부터 파이에 있다 ([0023](0023-robot-controller.md)).

## 근거

- 0023의 생각(응용과 상관없는 컨트롤러, 펜던트는 컨트롤러에 붙는다)은 컨트롤러가 개발 PC와 떨어져 있을 때 온전히 된다.
- PC 부하가 실행 루프에 닿는 문제를 줄이는 데서 그치지 않고 구조로 없앤다.
- 파이가 이미 세 대 있어 사는 것이 없다. 더 드는 일(네트워크 API, 배포 명령, 시뮬레이션 컨트롤러)은 대부분 0023으로 가면 어차피 할 일이고, 처음 한 번 드는 일이다.
- 언어는 컨트롤러가 도는 곳을 따른다. 지금은 Python 코드가 0024 만드는 순서 1번뿐이라 바꾸는 비용이 가장 작다.
- 단계로 나누면 관절 하나 시험까지는 A와 거의 같다. 더 드는 시간은 팔 움직이기(시뮬레이션 연결, 배포)와 PC 없이 쓰기에 몰린다.

## 영향

- 0005는 "대체됨 (0025)"이 된다. [0007](0007-repo-structure.md)(Rust 크레이트 자리), [0008](0008-environment-and-packages.md)(서보 SDK, Rust), 0009(실행 루프의 자리와 언어), 0023(정할 것 5번), 0024(Rust로 짠다)를 고쳤다.
- Rust 워크스페이스를 만들었다 (2026-11-11): `crates/servo`와 `crates/bench`([0007](0007-repo-structure.md)), 도구 모음 판 고정(`rust-toolchain.toml`), `.gitignore`의 `target/`, [CLAUDE.md](../../CLAUDE.md#자주-쓰는-명령)의 커밋 전 검사에 cargo fmt·clippy·test, [conventions.md](../conventions.md)의 Rust 규칙(주석은 한국어, 단위 규칙은 Python과 같다). `crates/controller`는 첫 코드를 넣을 때 만든다.
- Python으로 만든 0024 만드는 순서 1번(`packages/servo`의 `horilab_servo.feetech`)은 기준 구현으로 남긴다. 실물에서 첫 덤프를 뜨고 Rust 버스와 결과를 맞춰 보는 데 쓰고, Rust 버스가 실물에서 확인되면 지운다. 컨트롤러와 이야기하는 Python 쪽은 따로 클라이언트(`packages/client`)로 만든다 (전송은 [0023](0023-robot-controller.md)의 WSS).
- Rust 서보 라이브러리 rustypot(Pollen, Apache-2.0)을 0024의 확인 항목(지난 값을 돌려주지 않는지, 서보마다 결과, 상태 바이트, EEPROM 잠금, 타임아웃, 섞인 모델, ST-3120)으로 평가했다 (2026-11-11). 동기 읽기가 서보 하나만 실패해도 통째로 실패하고 잠금을 LeRobot식으로 다뤄서, 참고만 하고 서보 버스를 직접 짰다 ([0024](0024-servo-bus.md)의 검토한 대안).
- 팔 움직이기 전에 정할 것 (리서치의 추천, [controller-research.md](../controller-research.md#4-시뮬레이션-연결과-파이용-계획-라이브러리)):
  - 경로 계획(IK, 궤적)을 무엇으로 어디에 짤지. 지금 결정대로면 팔 움직이기에서 PC에 Python으로 짜고, PC 없이 쓰기에서 컨트롤러 안에 Rust로 다시 짠다. [0023](0023-robot-controller.md)에서 IK·이동 명령·조그를 컨트롤러의 일로 정해서, 처음부터 컨트롤러 안에 Rust로 짜면 한 번만 짜고 폰·게임패드의 직교 조그도 처음부터 PC 없이 된다. 대신 팔이 처음 움직이기까지 시간이 더 든다. 정하면 [0007](0007-repo-structure.md)에 자리를 더한다.
  - 시뮬레이션 백엔드를 붙이는 방법. 추천은 Python MuJoCo 시뮬레이션 서버(`packages/sim`)를 TCP로 붙이는 것이다.
    - 컨트롤러의 서보 버스 자리에 인터페이스를 두고, 실물(Feetech 시리얼)과 시뮬레이션 서버 두 구현을 둔다. 그 위의 ID 대응, 방향·영점 변환, 안전 검사, 실패 세기가 실물과 같게 시험된다.
    - 매 박자 목표를 보내면 시뮬레이션이 한 주기만큼 진행해 상태로 답한다 (PX4의 lockstep 방식). 시험용 빠른 모드와, 뷰어·펜던트용 실시간 모드를 둔다.
    - 장면, 카메라, 뷰어는 Python에 남는다. 같은 TCP로 파이의 컨트롤러를 PC 시뮬레이션에 붙일 수도 있다.
    - Rust에서 MuJoCo를 직접 부르는 길(mujoco-rs)은 판마다 API가 깨져서 대안으로 둔다.
  - 빌드, 배포, 파이 실시간 환경은 [0026](0026-pi-runtime-deploy-records.md)에서 정했다.
- PC 없이 쓰기 전에 정할 것: 파이에서 돌릴 경로 계획. 리서치의 추천:
  - IK: 우리 팔은 평행 축 셋 꼴이라 닫힌 해가 있다. IK-Geo의 그 풀이만 Rust로 옮기고 PC의 EAIK와 대조해 검증한다. Python으로 둔다면 EAIK는 파이(aarch64)용 휠이 있다.
  - 궤적: 조그, 관절 이동, 재생, 관절 공간 블렌드는 순수 Rust인 rsruckig(MIT)로 한다. 반지름 블렌드가 있는 직선 이동은 기하 블렌드 → 같은 해 가지의 IK → 시간 매기기로 하고, 시간 매기기 도구(TOPP-RA C++, copp)는 재 보고 고른다.
- 랜: PC와 두 파이를 유선으로 잇는다. 파이 자리와 집 네트워크(공유기 포트, 스위치)를 정할 때 랜 케이블 수를 다시 센다. [부품표](../bom.md)의 랜 케이블은 지금 하나다.
- 서보 어댑터와 PC를 잇는 5 m USB 2 케이블은 개발할 때(관절 하나 시험 등) 쓴다. 컨트롤러 파이에서는 짧은 케이블이면 된다.
- 0005와 0009가 제작 로드맵 2단계에 하기로 한 부하 시험(영상 처리를 돌린 채 몇 시간 동안 명령 간격과 통신 오류를 기록)은 컨트롤러 파이에서 한다.

## 바뀐 점

- 2026-11-11: 파이는 로봇을 쓸 때만 켜고, 안 쓸 때는 멀티탭까지 끈다. 컨트롤러가 파이에 "늘 있다"고 적었던 것은 켜진 PC를 따라다니지 않는다는 뜻이라 고쳐 적었다. 끄는 절차와 전원 끊김 대비는 [0026](0026-pi-runtime-deploy-records.md)의 7이다.
- 2026-11-11: [0023](0023-robot-controller.md)으로 모터 프로세스가 API와 조종권까지 맡는 컨트롤러가 되어서 "모터 프로세스"를 "컨트롤러"로 바꿔 부른다. 크레이트는 `crates/servo`와 `crates/controller`로 나눴다 ([0007](0007-repo-structure.md)). 경로 계획을 처음부터 컨트롤러 안에 Rust로 짤지를 "팔 움직이기 전에 정할 것"에 더했다. 0023에서 펜던트 화면은 컨트롤러가 직접 열기로 해서, PC 없이 쓰기 단계에서 옮길 것은 경로 계획만 남았다.
