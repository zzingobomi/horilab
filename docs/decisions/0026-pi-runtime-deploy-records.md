# 0026. 컨트롤러 파이의 실행 환경, 배포, 기록 넘기기, NAS 쓰임

- 상태: 채택
- 날짜: 2026-11-10

## 배경

- 모터 프로세스는 Rust로 짜서 로봇 옆 컨트롤러 파이에서 늘 돌린다. 2단계(팔 움직이기)에서 파이 배포 명령을 만든다 ([0025](0025-controller-on-pi.md)).
- 시험 기록은 rclone으로 구글 드라이브 `horilab/` 아래에 레포와 같은 경로로 비춘다. 지금까지는 실물이 있는 PC가 올렸다 ([0022](0022-records-and-sync.md)). 컨트롤러가 파이로 가면 기록은 파이에서 생긴다.
- 실물이 있는 PC에서 파이 세 대, NAS, PC, 집 네트워크를 확인하고 패키지를 올렸다 (2026-11-10, [hardware.md](../hardware.md#가진-것)). 그 뒤 [0023](0023-robot-controller.md)의 남은 리서치(파이 컨트롤러, NAS)를 했다. 대안과 자료는 [controller-research.md](../controller-research.md) 5·6절에 있다.

## 결정

1. **OS**: 컨트롤러 파이는 2단계에서 Ubuntu 26.04 LTS로 바꾼다.
   - 먼저 부트로더를 올린다. 26.04는 파이 4에 2022-11-25 이후 부트로더를 요구하는데, 가진 세 대는 그보다 옛날이고 22.04 패키지로는 올릴 수 없다 ([hardware.md](../hardware.md#가진-것)). PC의 Raspberry Pi Imager로 부트로더 업데이트용 SD를 만들어 한 번 켠다.
   - 새 SD 카드에 깔아 여분 파이에서 먼저 확인한다: 부팅, 어댑터가 `/dev/serial/by-id/` 경로로 잡히는지, 서보 읽기, 재부팅과 전원 차단 뒤 복구, 실시간 커널 설치. 지금 SD는 그대로 둬서 언제든 되돌린다.
   - 막히면 24.04로 간다 (실시간 커널은 Ubuntu Pro로 켜고, 개인 5대까지 무료다).
   - 카메라 파이는 pyrealsense2 소스 빌드가 22.04에 묶여 있어 따로 정한다.
2. **실시간**: 하나씩 켜며 잰다. 기본 → 실행 루프 스레드에 실시간 우선순위(SCHED_FIFO)와 mlockall → 코어 3 고정(`isolcpus=3`) → 인터럽트를 0~2번 코어로(`irqaffinity=0-2`) → 클럭 정책 performance → 그래도 모자라면 실시간 커널(`linux-raspi-realtime`).
   - 우선순위는 80에서 시작해 재서 정한다. 99는 커널의 감시 스레드 몫이다.
   - 잴 값: 주기의 평균과 최대, 10 ms를 넘긴 횟수, 계산 시간과 버스 시간(따로), 응답 없음과 다시 보낸 횟수. 웹 서버, 기록 쓰기, 업로드를 켠 채 몇 시간 잰다.
   - 기록 쓰기와 업로드는 0~2번 코어에서 가장 낮은 우선순위로 돈다. 코어 3을 떼어 줘도 서보 응답을 받아 넘기는 커널 쪽 일은 0~2번 코어에서 돌기 때문이다.
   - 자가 점검에 부팅 인자와 우선순위가 실제로 걸렸는지 넣는다.
3. **빌드**: PC에서 cargo-zigbuild로 `aarch64-unknown-linux-musl` 정적 실행 파일을 만든다.
   - 모터 프로세스에는 C 라이브러리가 끼는 크레이트를 넣지 않는다.
   - 부하 측정 때 glibc판(`aarch64-unknown-linux-gnu.2.35`)도 한 번 돌려 보고, 차이가 있으면 바꾼다.
   - 판마다 디버그 정보가 남은 실행 파일도 둔다.
   - 판 내기와 검사는 나중에 GitHub의 무료 arm64 러너로 옮긴다.
4. **배포**:
   - 처음 재는 동안은 실행 파일을 scp로 손으로 올린다. 컨트롤러를 늘 돌리기 시작할 때 `uv run tools/deploy.py`의 `deploy`, `rollback`, `status`를 만든다.
   - 판마다 `/opt/horilab/releases/<날짜시각>-<커밋>/`에 실행 파일과 그 판의 로봇 설정을 둔다. 임시 폴더에 올려 SHA-256을 맞춰 본 뒤 판 폴더로 옮기고, `current` 링크는 한 번에 바꾼다 (새 링크를 만들어 이름을 바꾼다). 최근 몇 판만 남긴다.
   - 컨트롤러가 쉬는 상태일 때만 바꾸고, 할 일을 보여 준 뒤 `--yes`를 받는다. 새 판이 판 번호와 자가 점검을 답하지 않으면 이전 판으로 되돌린다.
   - 새 판이나 되돌린 판이 켜져도 토크 상태와 서보의 목표를 바꾸지 않고, 움직임은 사람이 다시 명령해야 시작한다 ([0009](0009-control-architecture.md#안전)).
   - 처음 설정(사용자, 폴더, systemd 유닛, 재시작만 허용하는 sudo 규칙, 부팅 인자, journald 상한, rclone)은 레포의 스크립트로 한다.
   - 파이마다 git pull하고 빌드하지 않는다. NAS, 컨테이너, Ansible은 쓰지 않는다.
   - 컨트롤러를 파이에서 처음 돌릴 때 파이 재부팅 시험을 한다. 부팅 때 저절로 켜진 모터 프로세스가 토크와 목표를 바꾸지 않는지, 어댑터를 같은 경로로 다시 찾는지, 시각이 맞기 전에 시작한 기록에 그 표시가 남는지 본다. 서보 쪽 끊김 시험(명령 끊김, 프로그램 다시 켜기, 서보 전원)은 관절 시험에서 한다 ([joint-test.md](../joint-test.md#순서)).
5. **기록**:
   - 파이는 `/var/lib/horilab/` 아래, 레포와 같은 상대 경로(`records/…`)에 세션 단위로 쓴다 (형식은 [0024](0024-servo-bus.md)). 파이 4에는 RTC가 없어서 시각이 맞았는지도 남긴다.
   - 세션이 끝나면 `meta.json`에 끝난 방식(정상, 보호 정지, 오류)과 끝난 시각을 더한다. 이것이 없으면 중간에 끊긴 세션이다.
   - 실행 루프는 파일에 쓰지 않는다. 기록은 메모리 줄에 넣기만 하고, 다른 코어의 낮은 우선순위 스레드가 모아서 1초쯤마다 쓴다. 줄이 차면 루프는 기다리지 않고 기록을 버리며, 버린 수를 센다.
   - 늘 켜 두는 기록은 메모리 링 버퍼에만 두고, 보호 정지·오류 때 파일로 남긴다. 프로그램 로그는 journald에 상한을 두고 남긴다. SD에 스왑을 두지 않는다.
   - 파이가 systemd 타이머(몇 분마다, 2분 넘게 안 바뀐 파일만: `--min-age 2m`)와 시험 끝에서 `rclone copy --update`로 드라이브에 올린다. 업로드는 CPU와 디스크를 가장 낮은 우선순위로 쓰고 속도 상한을 둔다. 플래그는 `tools/sync.py`에서 가져와 두 곳에 따로 적지 않는다.
   - 파이에 남은 기록은 드라이브에 같은 파일이 있는지 확인한 세션만, 30일이 지나면 지운다. 남은 공간이 5 GB 아래면 새 기록 세션을 시작하지 않고 알린다. 제어는 그대로 돈다.
   - 업로드는 별도 시스템 사용자로 돌린다. 이 사용자는 서보 장치를 쓰지 못하고(dialout 그룹에 넣지 않는다), rclone 설정은 이 사용자만 읽는다. 파이마다 따로 로그인한다.
6. **NAS**: 배포와 기록의 길목에 두지 않는다. 맡는 일은 넷이다.
   - Cloud Sync로 드라이브 `horilab/`을 "내려받기만, 지우지 않기"로 보관한다. 드라이브가 원본이고 NAS는 사본이다 (NAS 디스크는 하나다).
   - 파이 SD 카드 이미지를 보관한다.
   - 기록을 늘 켜 두기로 정해 드라이브가 모자라면, NAS가 파이에서 끌어와 모두 보관하고 고른 것만 드라이브에 올리는 허브로 바꾼다.
   - 밖에서 집에 들어올 일이 생기면 Tailscale 서브넷 라우터를 맡는다.

## 근거

- 1: 22.04에는 파이용 실시간 커널이 없고 표준 지원이 2027-05에 끝난다. 26.04는 2031-05까지 지원하고, 파이용 실시간 커널을 apt로 무료로 깔며, 파이 4B 인증을 받았다. 24.04는 Pro 등록이 필요하고 지원이 2년 짧다. 새 SD로 시험하면 지금 SD가 그대로 되돌릴 판이 된다.
- 2: 부하가 있을 때 최악 지연을 줄이는 데는 실시간 우선순위와 코어 격리가 먼저 듣는다는 측정이 있다. 하나씩 켜야 무엇이 들었는지 알고, 실시간 커널은 되돌리기 어려운 쪽이라 마지막에 둔다.
- 3: 20스레드 PC가 가장 빠르고 Docker가 필요 없다. musl 정적 실행 파일은 OS 판과 상관없이 돈다. glibc판은 같은 도구에서 대상만 바꾸면 되므로 비교 시험을 따로 만들지 않는다. 공개 레포의 arm64 러너는 무료다.
- 4: 실행 파일 하나라 복사와 링크 전환이 가장 단순하고, 되돌리기가 링크 하나다. 설정이 판과 같이 묶여 되돌리기에 설정까지 따라온다. 로봇이 움직이는 중에는 바꾸지 않는다. SHA-256은 끊긴 전송이나 덜 올라간 파일을 잡는다. 재는 동안은 판이 자주 바뀌어 손으로 올려도 충분하다. 프로세스 종료와 재부팅은 복구 길(부팅 순서, 장치 다시 찾기, 시각 맞추기)이 달라 따로 본다.
- 5: PC와 NAS가 꺼져 있어도 기록이 드라이브에 간다.
  - 완료 표시가 있는 세션만 올리면 중간에 끊긴 세션(가장 궁금한 기록)이 올라가지 않는다. 그래서 2분 넘게 안 바뀐 파일을 올리고, 끝난 방식은 `meta.json`으로 가른다.
  - SD는 쓰는 중에 잠깐씩 멈출 수 있다. 실행 루프가 파일을 만지지 않아야 제어 주기가 SD에 매이지 않는다.
  - 양 (어림): 팔 전체를 100 Hz로 다 남겨도 하루 2시간이면 0.5 GB쯤, 1년에 200 GB 안팎이라 64 GB 카드와 쓰기 수명에 여유가 있다. 카드마다 수명이 달라서 확인은 못 했다.
  - 파이에 놓이는 드라이브 토큰은 사용자 분리와 SSH 키로 위험을 줄인다. 업로드 사용자가 서보 장치를 못 쓰면 토큰이 새도 로봇은 움직이지 못한다.
- 6: NAS는 CPU가 2코어라 빌드가 느리고(데스크톱의 약 1/20), 커널 4.4라 arm64 컨테이너를 못 돌린다. 공개 레포의 자체 호스팅 러너는 GitHub가 권하지 않는다. 길목에 끼우면 단계만 늘고 NAS가 꺼질 때 같이 멈춘다.

## 영향

- [0009](0009-control-architecture.md)의 안전 표를 고쳤다: 모터 프로세스만 다시 켜질 때와 서보 전원이 꺼졌다 켜질 때를 나눈다.
- [joint-test.md](../joint-test.md)의 순서에 끊김 확인을 더했다.
- 2단계 일에 더한다: `tools/deploy.py`와 처음 설정 스크립트, [setup.md](../setup.md) 절차, `tools/sync.py`의 `RCLONE_SHA256`에 `linux-arm64`, 파이 업로드 타이머와 오래된 기록 지우기.
- PC의 Rust(1.80)를 올린다. cross는 1.85, mujoco-rs는 1.95 이상이 필요하다.
- 게임패드 크레이트는 evdev를 같이 따진다 (0023의 8번).
- 직접 할 일: 남는 microSD 카드와 PC에 꽂을 SD 카드 리더가 있는지 본다. 없으면 살 것을 골라 알린다 (컨트롤러 파이용은 고내구성 카드를 권한다). 부트로더를 올리고 여분 파이에서 26.04를 시험한다. 파이 세 대의 SD 이미지를 떠서 NAS에 둔다 (카메라 파이 먼저). NAS Cloud Sync에 구글 로그인을 한다.
- 실물로 확인할 것은 controller-research.md 5·6절 끝에 있다.
