# 0026. 컨트롤러 파이의 실행 환경, 배포, 기록 넘기기, NAS 쓰임

- 상태: 채택
- 날짜: 2026-11-10

## 배경

- 컨트롤러는 Rust로 짜서 로봇 옆 컨트롤러 파이에서 돌린다. 파이는 로봇을 쓸 때만 켜고, 안 쓸 때는 멀티탭까지 끈다 (7). 팔 움직이기 단계([0025](0025-controller-on-pi.md))에서 파이 배포 명령을 만든다.
- 시험 기록은 rclone으로 구글 드라이브 `horilab/` 아래에 레포와 같은 경로로 비춘다. 지금까지는 실물이 있는 PC가 올렸다 ([0022](0022-records-and-sync.md)). 컨트롤러가 파이로 가면 기록은 파이에서 생긴다.
- 실물이 있는 PC에서 파이 세 대, NAS, PC, 집 네트워크를 확인하고 패키지를 올렸다 (2026-11-10, [hardware.md](../hardware.md#가진-것)). 그 뒤 [0023](0023-robot-controller.md)의 남은 리서치(파이 컨트롤러, NAS)를 했다. 대안과 자료는 [controller-research.md](../controller-research.md) 5·6절에 있다.

## 결정

1. **OS**: 컨트롤러 파이는 팔 움직이기 단계에서 Ubuntu 26.04 LTS로 바꾼다.
   - 먼저 부트로더를 올린다. 26.04는 파이 4에 2022-11-25 이후 부트로더를 요구하는데, 가진 세 대는 그보다 옛날이고 22.04 패키지로는 올릴 수 없다 ([hardware.md](../hardware.md#가진-것)). PC의 Raspberry Pi Imager로 부트로더 업데이트 이미지를 SD 카드에 써서 그 파이를 한 번 켠다.
   - 여분 파이(hori3)에서 먼저 확인한다. hori3의 SD 카드를 통째 이미지로 떠서 NAS에 둔 뒤, 그 카드로 부트로더를 올리고 26.04를 깐다. 되돌릴 때는 떠 둔 이미지를 다시 쓴다. 확인할 것: 부팅, 어댑터가 `/dev/serial/by-id/` 경로로 잡히는지, 서보 읽기, 재부팅과 전원 차단 뒤 복구(기록을 쓰는 중에 전원을 수십 번 끊어 본다, 7), 실시간 커널 설치, PC에서 빌드한 실행 파일이 도는지. 이어서 2의 미리 재기를 한다.
   - 막히면 24.04로 간다 (실시간 커널은 Ubuntu Pro로 켜고, 개인 5대까지 무료다).
   - 카메라 파이는 pyrealsense2 소스 빌드가 22.04에 묶여 있어 따로 정한다.
2. **실시간**: 컨트롤러를 만들기 전에 여분 파이(hori3)에서 미리 잰다. 조정은 하나씩 켜며 잰다: 기본 → 실행 루프 스레드에 실시간 우선순위(SCHED_FIFO)와 mlockall → 코어 3 고정(`isolcpus=3`) → 인터럽트를 0~2번 코어로(`irqaffinity=0-2`) → 클럭 정책 performance. 실시간 커널(`linux-raspi-realtime`)도 hori3에서 같이 재서, 컨트롤러 파이에 처음부터 켤지 정한다.
   - 미리 재기 (hori3):
     1. 26.04를 깐 뒤: 지연 측정 도구(cyclictest)를 돌리며 부하 도구(stress-ng)로 CPU, SD, 네트워크에 부하를 건다. 일반 커널(조정을 하나씩)과 실시간 커널을 둘 다 잰다. 온도와 클럭도 같이 남긴다.
     2. 0024 만드는 순서 1번(Rust 서보 버스, 가짜 서보)이 되면: 가짜 서보 7개(그리퍼 포함)에 첫 연결 때 잰 버스 시간을 넣어, 100 Hz 실행 루프를 흉내 낸 시험 프로그램(`crates/bench`의 `runloop`)을 같은 부하로 몇 시간 돌린다. 22.04(커널 5.15 PREEMPT, 실시간 커널 아님)에서 잰 값 (2026-11-12 ~ 13, 기록은 `records/bench/`):
        - 부하는 stress-ng(CPU 4, 메모리 256 MB, SD에 fsync 쓰기, 입출력)와 iperf3(hori1과 보내기·받기 각 200 Mbit/s)다. 클럭은 늘 1800 MHz였고, 온도는 최고 76.9 °C였으며 클럭 제한은 걸리지 않았다.
        - 보통 스케줄링(SCHED_OTHER) 10분: 깨어나는 지연 최악 36.0 ms, 놓친 박자 164번.
        - SCHED_FIFO 80 + mlockall: 10분 판은 최악 0.47 ms였지만 1시간 판은 최악 2.21 ms였다 (1 ms를 넘은 박자가 36만 박자 중 27개). 놓친 박자는 0번.
        - 여기에 실행 루프를 코어 3에 묶고 인터럽트를 0~2번 코어로 옮긴 2시간 판(`/proc/irq`로 옮김): 99.99%가 0.24 ms(묶기 전 0.90 ms)로 줄었지만, 최악은 1.15 ms로 기준을 넘었다 (72만 박자 중 1개). 놓친 박자는 0번이다. 깨어나는 지연과 일하는 시간의 최악을 더해도 6.1 ms라 한 박자(10 ms) 안이다.
        - 10분 판은 통과해도 몇 시간 판에서 넘으므로, 판정은 몇 시간 판으로만 한다.
        - Ubuntu에 기본으로 켜진 irqbalance가 유선랜 인터럽트 하나를 코어 3에 두었다. 부팅 인자로 `isolcpus=3 irqaffinity=0-2`를 주면 irqbalance도 코어 3을 피한다.
        - 부팅 인자 `isolcpus=3 irqaffinity=0-2`로 코어 3을 떼어 내고 실행 루프를 코어 3에 묶은 3시간 판 (2026-11-12 밤): 깨어나는 지연의 최악은 클럭 정책 ondemand에서 0.23 ms(99.99%는 0.16 ms), performance에서 0.15 ms(0.13 ms)다. 두 판 모두 108만 박자 동안 1 ms를 넘은 박자와 놓친 박자가 없어 통과 기준을 지킨다. 일하는 시간의 최악은 4.2 ms라 깨어나는 지연과 더해도 4.4 ms다. 밤새 코어 3에는 시계 인터럽트와 코어 사이 알림만 왔고, 랜과 SD 카드 인터럽트는 오지 않았다. stress-ng는 코어 3을 쓰지 못해 나머지 세 코어에서 돌았다. 온도는 최고 69.6 °C였고 클럭 제한은 걸리지 않았다.
        - 부하 없는 30분 판은 최악 0.05 ms 안팎이다. 깨어나는 지연의 중간값은 performance 0.008 ms, ondemand 0.022 ms다.
        - 그래서 22.04 일반 커널에서도 SCHED_FIFO 80, mlockall, 코어 3 고정, 부팅 인자 `isolcpus=3 irqaffinity=0-2`로 기준을 지킨다. 클럭 정책은 performance로 한다. 통과에 꼭 필요하지는 않지만 최악과 쉴 때의 지연이 더 짧고, 부하를 건 판에서도 클럭 제한이 걸리지 않았다. 26.04로 바꾸면 커널이 바뀌므로 같은 3시간 판을 다시 잰다.
     3. 경로 계획을 고르기 전에: 후보(rsruckig, IK)와 충돌 검사(자기 충돌, 안전 평면)의 한 번 계산 시간을 잰다.
     4. Rust 버스가 되면: 어댑터를 hori3에 꽂고 서보 7개를 이어 Rust로 버스 왕복 시간을 잰다 (0024 만드는 순서 6번).
   - 통과 기준 (재기 전에 정한다): 부하를 건 채 몇 시간 동안 깨어나는 지연이 최악 1 ms 안, 놓친 박자 0번, 직교 조그의 IK와 충돌 검사 한 번이 1 ms 안, 새 이동 명령의 계획이 0.1초 안.
   - 모자라면 이 순서로 고른다: 우리 코드 고치기(계산을 덜 자주, 실행 루프 밖에서) → 실시간 커널 → 실행 루프 주기 낮추기(100 → 50 Hz) → 그래도 안 되면 파이 5. 파이 5는 예산이 들어 사용자와 정한다.
   - 우선순위는 80에서 시작해 재서 정한다. 99는 커널의 감시 스레드 몫이다.
   - 잴 값: 주기의 평균과 최대, 놓친 박자 수, 계산 시간과 버스 시간(따로), 응답 없음과 다시 보낸 횟수. 컨트롤러 파이에서도 웹 서버, 기록 쓰기, 업로드를 켠 채 몇 시간 잰다.
   - 기록 쓰기와 업로드는 0~2번 코어에서 가장 낮은 우선순위로 돈다. 코어 3을 떼어 줘도 서보 응답을 받아 넘기는 커널 쪽 일은 0~2번 코어에서 돌기 때문이다.
   - 자가 점검에 부팅 인자와 우선순위가 실제로 걸렸는지 넣는다.
3. **빌드**: PC에서 cargo-zigbuild로 `aarch64-unknown-linux-musl` 정적 실행 파일을 만든다.
   - cargo-zigbuild와 zig는 uv 개발 의존성으로 레포 환경에 두고(PC에 따로 깔지 않는다), `uv run tools/pi_build.py`로 부른다.
   - 컨트롤러에는 시스템 C 라이브러리(libudev 등)를 링크하는 크레이트를 넣지 않는다. C 소스를 같이 빌드하는 크레이트(TLS의 ring, aws-lc-rs)는 zig로 빌드돼 정적 실행 파일이 된다 (2026-11-11 확인).
   - glibc판(`aarch64-unknown-linux-gnu.2.35`)은 부하를 건 실행 루프 시험(10분, 2의 미리 재기 2)에서 musl판과 지연 차이가 보이지 않았다. 그래서 musl을 쓴다.
   - 판마다 디버그 정보가 남은 실행 파일도 둔다.
   - 판 내기와 검사는 나중에 GitHub의 무료 arm64 러너로 옮긴다.
4. **배포**:
   - 처음 재는 동안은 실행 파일을 scp로 손으로 올린다. 컨트롤러를 파이에서 쓰기 시작할 때 `uv run tools/deploy.py`의 `deploy`, `rollback`, `status`를 만든다.
   - 판마다 `/opt/horilab/releases/<날짜시각>-<커밋>/`에 실행 파일과 그 판의 로봇 설정을 둔다. 임시 폴더에 올려 SHA-256을 맞춰 본 뒤 판 폴더로 옮기고, `current` 링크는 한 번에 바꾼다 (새 링크를 만들어 이름을 바꾼다). 최근 몇 판만 남긴다.
   - 컨트롤러가 쉬는 상태일 때만 바꾸고, 할 일을 보여 준 뒤 `--yes`를 받는다. 새 판이 판 번호와 자가 점검을 답하지 않으면 이전 판으로 되돌린다.
   - 새 판이나 되돌린 판이 켜져도 토크 상태와 서보의 목표를 바꾸지 않고, 움직임은 사람이 다시 명령해야 시작한다 ([0009](0009-control-architecture.md#안전)).
   - 처음 설정(사용자, 폴더, systemd 유닛, 재시작만 허용하는 sudo 규칙, 부팅 인자, journald 상한, rclone)은 레포의 스크립트로 한다.
   - 파이마다 git pull하고 빌드하지 않는다. NAS, 컨테이너, Ansible은 쓰지 않는다.
   - 컨트롤러를 파이에서 처음 돌릴 때 파이 재부팅 시험을 한다. 부팅 때 저절로 켜진 컨트롤러가 토크와 목표를 바꾸지 않는지, 어댑터를 같은 경로로 다시 찾는지, 시각이 맞기 전에 시작한 기록에 그 표시가 남는지 본다. 서보 쪽 끊김 시험(명령 끊김, 프로그램 다시 켜기, 서보 전원)은 맨 서보 확인에서 한다 ([0028](0028-ur-style-joints.md)의 시험과 측정).
5. **기록**:
   - 파이는 `/var/lib/horilab/` 아래, 레포와 같은 상대 경로(`records/…`)에 세션 단위로 쓴다 (형식은 [0024](0024-servo-bus.md)). 파이 4에는 RTC가 없어서 시각이 맞았는지도 남긴다.
   - 세션이 끝나면 `meta.json`에 끝난 방식(정상, 보호 정지, 오류)과 끝난 시각을 더한다. 이것이 없으면 중간에 끊긴 세션이다.
   - 실행 루프는 파일에 쓰지 않는다. 기록은 메모리 줄에 넣기만 하고, 다른 코어의 낮은 우선순위 스레드가 모아서 1초쯤마다 쓴다. 줄이 차면 루프는 기다리지 않고 기록을 버리며, 버린 수를 센다.
   - 늘 켜 두는 기록은 메모리 링 버퍼에만 두고, 보호 정지·오류 때 파일로 남긴다. 프로그램 로그는 journald에 상한을 두고 남긴다. SD에 스왑을 두지 않는다.
   - 파이가 systemd 타이머(몇 분마다, 2분 넘게 안 바뀐 파일만: `--min-age 2m`), 시험 끝, 끄기 절차에서 `rclone copy --update`로 드라이브에 올린다. 켤 때는 못 올린 기록부터 올린다. 업로드는 CPU와 디스크를 가장 낮은 우선순위로 쓰고 속도 상한을 둔다. 플래그는 `tools/sync.py`에서 가져와 두 곳에 따로 적지 않는다.
   - 파이에 남은 기록은 드라이브에 같은 파일이 있는지 확인한 세션만, 30일이 지나면 지운다. 남은 공간이 5 GB 아래면 새 기록 세션을 시작하지 않고 알린다. 제어는 그대로 돈다.
   - 업로드는 별도 시스템 사용자로 돌린다. 이 사용자는 서보 장치를 쓰지 못하고(dialout 그룹에 넣지 않는다), rclone 설정은 이 사용자만 읽는다. 파이마다 따로 로그인한다.
6. **NAS**: 배포와 기록의 길목에 두지 않는다. 맡는 일은 넷이다.
   - Cloud Sync로 드라이브 `horilab/`을 "내려받기만, 지우지 않기"로 보관한다. 드라이브가 원본이고 NAS는 사본이다 (NAS 디스크는 하나다).
   - 파이 SD 카드 이미지를 보관한다.
   - 기록을 늘 켜 두기로 정해 드라이브가 모자라면, NAS가 파이에서 끌어와 모두 보관하고 고른 것만 드라이브에 올리는 허브로 바꾼다.
   - 밖에서 집에 들어올 일이 생기면 Tailscale 서브넷 라우터를 맡는다.
7. **켜고 끄기**: 로봇을 쓸 때만 켜고, 안 쓸 때는 멀티탭까지 끈다. 서보 전원도 같이 꺼진다.
   - 끌 때: 끄기 명령(펜던트나 게임패드, 그 전에는 PC에서) → 팔을 쉬는 자세로 옮기고 토크를 끈다 → 기록을 닫고 남은 기록을 올린다(시간 상한을 둔다) → OS를 끈다 → 펜던트에 꺼도 된다고 띄운다 → 서보 전원의 + 플러그를 뺀다 → 멀티탭을 끈다. 쉬는 자세는 토크 없이 팔이 받쳐지는 자세이고, 팔을 설계할 때 정한다.
   - 절차를 잊고 멀티탭을 꺼도 견디게 한다. 기록은 이어 쓰며 1초쯤마다 디스크에 확정하고(5), 못 올린 기록은 다음에 켤 때 올린다. 기록을 쓰는 중에 전원이 끊겨도 SD 카드와 파일 시스템이 견디는지 hori3에서 수십 번 끊어 보고, 못 견디면 읽기 전용 루트를 따진다.
   - 켤 때: + 플러그를 뺀 채 멀티탭과 가변 전원을 켜고, 화면에서 12.0 V를 본 뒤 + 플러그를 꽂는다 ([0016](0016-servo-power.md)). 서보는 토크가 꺼진 채 켜진다(메모리 표의 초기값). 컨트롤러는 토크를 켜지 않고 사람의 명령을 기다리며([0009](0009-control-architecture.md#안전)), 시각이 맞기 전의 기록에는 그 표시를 남긴다(5).

## 근거

- 1: 22.04에는 파이용 실시간 커널이 없고 표준 지원이 2027-05에 끝난다. 26.04는 2031-05까지 지원하고, 파이용 실시간 커널을 apt로 무료로 깔며, 파이 4B 인증을 받았다. 24.04는 Pro 등록이 필요하고 지원이 2년 짧다. 여분 파이에서 시험하면 컨트롤러와 카메라 파이는 그대로 두고, 여분 파이는 떠 둔 이미지로 되돌린다. 그래서 카드를 새로 사지 않는다.
- 2: 다 만든 뒤에 부하가 모자란 것을 알면 고칠 길이 좁다. 파이 자체의 지연, 우리 실행 루프, 계산 시간은 실물이나 완성된 컨트롤러 없이 잴 수 있어서 먼저 잰다. 부하가 있을 때 최악 지연을 줄이는 데는 실시간 우선순위와 코어 격리가 먼저 듣는다는 측정이 있고, 하나씩 켜야 무엇이 들었는지 안다. 실시간 커널은 컨트롤러 파이에서는 되돌리기 어렵지만, hori3는 떠 둔 이미지로 되돌릴 수 있어서 미리 같이 잰다. 1 ms는 100 Hz 한 박자(10 ms)에서 버스가 쓰는 시간(2.2~5.7 ms, 추정)을 빼고도 남는 값이다.
- 3: 20스레드 PC가 가장 빠르고 Docker가 필요 없다. musl 정적 실행 파일은 OS 판과 상관없이 돈다. glibc판은 같은 도구에서 대상만 바꾸면 되므로 비교 시험을 따로 만들지 않는다. 공개 레포의 arm64 러너는 무료다.
- 4: 실행 파일 하나라 복사와 링크 전환이 가장 단순하고, 되돌리기가 링크 하나다. 설정이 판과 같이 묶여 되돌리기에 설정까지 따라온다. 로봇이 움직이는 중에는 바꾸지 않는다. SHA-256은 끊긴 전송이나 덜 올라간 파일을 잡는다. 재는 동안은 판이 자주 바뀌어 손으로 올려도 충분하다. 프로세스 종료와 재부팅은 복구 길(부팅 순서, 장치 다시 찾기, 시각 맞추기)이 달라 따로 본다.
- 5: PC와 NAS가 꺼져 있어도 기록이 드라이브에 간다.
  - 완료 표시가 있는 세션만 올리면 중간에 끊긴 세션(가장 궁금한 기록)이 올라가지 않는다. 그래서 2분 넘게 안 바뀐 파일을 올리고, 끝난 방식은 `meta.json`으로 가른다.
  - SD는 쓰는 중에 잠깐씩 멈출 수 있다. 실행 루프가 파일을 만지지 않아야 제어 주기가 SD에 매이지 않는다.
  - 양 (어림): 팔 전체를 100 Hz로 다 남겨도 하루 2시간이면 0.5 GB쯤, 1년에 200 GB 안팎이라 64 GB 카드와 쓰기 수명에 여유가 있다. 카드마다 수명이 달라서 확인은 못 했다.
  - 파이에 놓이는 드라이브 토큰은 사용자 분리와 SSH 키로 위험을 줄인다. 업로드 사용자가 서보 장치를 못 쓰면 토큰이 새도 로봇은 움직이지 못한다.
- 6: NAS는 CPU가 2코어라 빌드가 느리고(데스크톱의 약 1/20), 커널 4.4라 arm64 컨테이너를 못 돌린다. 공개 레포의 자체 호스팅 러너는 GitHub가 권하지 않는다. 길목에 끼우면 단계만 늘고 NAS가 꺼질 때 같이 멈춘다.
- 7: 끄는 일이 날마다 있어서 절차로 만든다. 서보 전원이 같이 꺼지면 브레이크 없는 팔이 떨어지므로 쉬는 자세가 먼저다. 절차를 잊는 날도 있으니 갑작스런 전원 끊김에 견디게 하고, 견디는지는 미리 잰다. 업로드 타이머만으로는 끄기 직전의 기록이 남는다.

## 영향

- [0009](0009-control-architecture.md)의 안전 표를 고쳤다: 컨트롤러만 다시 켜질 때와 서보 전원이 꺼졌다 켜질 때를 나눈다.
- 팔 움직이기 단계의 일에 더한다: `tools/deploy.py`와 처음 설정 스크립트, [setup.md](../setup.md) 절차, `tools/sync.py`의 `RCLONE_SHA256`에 `linux-arm64`, 파이 업로드 타이머와 오래된 기록 지우기, 끄기 명령과 켤 때 업로드.
- PC의 Rust(1.80)를 올린다. cross는 1.85, mujoco-rs는 1.95 이상이 필요하다.
- 게임패드 크레이트는 evdev를 같이 따진다 (0023의 8번).
- 직접 할 일: hori3의 SD 카드를 PC의 카드 리더로 통째 이미지로 떠서 NAS에 두고, 그 카드로 부트로더를 올린 뒤 26.04를 시험한다. 나머지 두 대의 SD 이미지도 떠 둔다 (카메라 파이 먼저). NAS Cloud Sync에 구글 로그인을 한다.
- 실물로 확인할 것은 controller-research.md 5·6절 끝에 있다.
