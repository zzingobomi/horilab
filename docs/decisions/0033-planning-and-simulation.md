# 0033. 경로 계획은 컨트롤러 안에 Rust로, 시뮬레이션은 Python MuJoCo 서버를 서보 버스 자리에 붙인다

- 상태: 채택
- 날짜: 2026-11-14

## 배경

- [0025](0025-controller-on-pi.md)는 팔 움직이기 전에 정할 것 둘을 남겼다: 경로 계획(IK, 궤적)을 무엇으로 어디에 짤지, 시뮬레이션 백엔드를 컨트롤러에 붙이는 방법. 조사는 [controller-research.md](../controller-research.md#4-시뮬레이션-연결과-파이용-계획-라이브러리)에 있다.
- 실행 루프의 뼈대, 기준값, 그리퍼는 가짜 서보로 만들었다 ([0032](0032-run-loop.md)). 가짜 서보에는 물리가 없어서 짐에 따른 처짐, 부하, 부딪힘을 시험하지 못한다.
- 설계 패키지에는 해석적 IK(EAIK, `horilab_design.ik`)와 MJCF 만들기(`horilab_design.mjcf`)가 있다.
- 팔은 아직 뽑지 않았다. 팔이 처음 움직이는 날은 출력, 조립, ST-3120 도착이 정한다.

## 검토한 대안

| 정할 것 | 대안 | 판단 |
|---|---|---|
| 경로 계획의 자리 | 팔 움직이기에서는 PC에 Python으로 짜고 PC 없이 쓰기에서 컨트롤러 안에 Rust로 다시 짠다 / 처음부터 컨트롤러 안에 Rust로 짠다 | 처음부터 컨트롤러 안에 Rust로 짠다. IK, 이동 명령, 조그는 컨트롤러의 일이다 ([0023](0023-robot-controller.md)). 한 번만 짜고, 시뮬레이션과 실물, PC와 파이가 같은 계획을 쓰며, 폰과 게임패드의 직교 조그도 처음부터 PC 없이 된다. 더 드는 시간은 팔이 처음 움직이는 날을 늦추지 않는다 (그날은 하드웨어가 정한다) |
| IK | ik-geo 크레이트 / mink / k / 직접 짜기 | 우리 팔의 꼴(J2·J3·J4가 평행)에 맞는 닫힌 해를 직접 짠다 (IK-Geo의 평행 축 셋 풀이). ik-geo 크레이트는 2024년에 멈췄고 LGPL인 NLopt를 cmake로 빌드한다. mink는 컨트롤러에 MuJoCo를 끌고 오고, k는 수치 풀이라 모든 해를 주지 않는다 |
| 궤적 | Ruckig(C++) / rsruckig / TOPP-RA / copp / 직접 짜기 | 조그, 관절 이동, 재생, 관절 공간 블렌드는 rsruckig(순수 Rust, MIT)로 한다. 직선 이동의 시간 매기기는 직접 짠다 (의존성 없음): 길의 곳마다 빠르기 상한을 두고 TOPP-RA와 같은 2차 풀이로 빠르기를 정한 뒤, 이동 평균 거르개로 저크를 제한한다. 관절 한계 때문에 늦춰야 하는 곳만 늦춘다. 같은 직선들에서 재 보았다 ([리서치](../controller-research.md#직선-이동에-재-본-값)): 저크를 제한한 시간 최적(copp TOPP3-LP)보다 평균 1.07배(가장 많이 1.39배) 오래 걸리고, 파이 4에서 직선 하나를 10 ms 안팎에 계산한다. TOPP3-LP는 4~5초를 계산하고, 시간 최적이라 늘 어느 한계에 붙어 움직이며, 의존성이 크고, 같은 풀이의 SOCP판은 같은 문제를 PC에서는 못 풀고 파이에서는 풀었다. TOPP-RA는 저크를 제한하지 않는다. 처음에 짠, 길 전체를 같은 비율로 늦추는 방식은 평균 1.30배(가장 많이 2.32배) 걸렸고, 특이 자세 가까이에서 23.9초였다 (고른 방식 4.5초, TOPP3-LP 4.2초) |
| 시뮬레이션 연결 | Rust가 MuJoCo를 직접 부름 / Python 시뮬레이션 서버를 서보 거래 단위로 TCP에 붙임 / Python이 Feetech 바이트를 흉내 냄 | Python 서버를 서보 거래 단위로 붙인다 (조사의 추천). 서보 버스 자리에 인터페이스를 두면, 그 위(관절 층의 ID 대응, 영점·방향 변환, 보호 비트, 통신 실패, 실행 루프)가 실물과 같은 코드로 시험된다. MuJoCo, 설계에서 만든 MJCF, 뷰어, 비전용 카메라 그림은 Python에 그대로 있고 MuJoCo 판은 Python만 맞춘다. Rust에서 MuJoCo를 부르는 크레이트는 판마다 API가 깨졌다. 바이트 흉내는 박자 신호가 따로 필요하고 더 느리며, 프로토콜 코드는 이미 가짜 서보로 시험한다 |

## 결정

- 경로 계획(IK, 이동 명령, 조그, 궤적)은 컨트롤러(`crates/controller`) 안에 Rust로 짠다.
  - IK: J2·J3·J4가 평행인 꼴의 닫힌 해를 직접 짜서 모든 해를 낸다. 관절 축과 링크 길이는 로봇 설정에서 읽는다 ([0009](0009-control-architecture.md)). 맞는지는 설계 패키지의 EAIK로 만든 자세와 해의 목록과 견주어 본다.
  - 궤적: rsruckig. 직선 이동의 시간 매기기는 직접 짠다 (`crates/controller/src/timing.rs`, 만드는 순서 3).
- 시뮬레이션: Python MuJoCo 시뮬레이션 서버(`packages/sim`)를 TCP로 붙인다.
  - 컨트롤러의 서보 버스 자리에 인터페이스(서보 거래: 핑, 읽기, 동기 읽기, 쓰기, 동기 쓰기)를 두고, 실물(Feetech 버스)과 시뮬레이션 두 구현을 둔다. 가짜 서보는 Feetech 버스 쪽 시험에 그대로 쓴다.
  - 한 걸음씩 간다 (PX4의 lockstep): 박자마다 동기 읽기가 오면 시뮬레이션이 한 주기만큼 물리를 진행하고 상태로 답한다. 실행 루프는 시뮬레이션 시간을 시계로 쓴다. 시험용 빠른 모드와 뷰어·펜던트용 실시간 모드를 둔다.
  - 시뮬레이션 서보는 실물 서보의 레지스터(토크 스위치, 목표, 토크 한도, 위치, 속도, 부하, 전압, 온도, 상태 바이트)를 같은 단위로 낸다. 위치 서보가 짐에 처지는 것과 토크 한도는 MuJoCo의 위치 액추에이터와 힘 한계로 흉내 내고, 게인은 다 만든 팔에서 잰 처짐에 맞춘다.
  - 같은 TCP로 파이의 컨트롤러를 PC의 시뮬레이션에 붙일 수 있다.
- 만드는 순서:
  1. 서보 버스 인터페이스와 시뮬레이션 서버. 실행 루프를 시뮬레이션으로 시험한다.
     - 서보 버스 인터페이스(`ServoBus`, `crates/servo/src/feetech/bus.rs`)를 두었다 (2026-11-14). 관절 층과 실행 루프는 이 거래만 쓰고, Feetech 버스(실물과 가짜 서보)가 그것을 낸다.
     - 시뮬레이션 서버(`packages/sim`)와 시뮬레이션 버스(`SimBus`, `crates/servo/src/sim.rs`)를 만들었다 (2026-11-14). 시뮬레이션은 설계를 불러오지 않고, 설계가 쓴 MJCF(`uv run python -m horilab_design.mjcf` → `build/sim/horibot.xml`)와 서보 사양(`params/servos.toml`)만 읽는다 ([0007](0007-repo-structure.md)). 거래는 TCP 위의 JSON 한 줄씩이고, 동기 읽기마다 한 주기만큼 진행한다. 서보는 관절 각 0이 서보 값 2048로 읽히게 달려 있다고 본다 (방향 +1). 위치 액추에이터의 강성은 STS3250이 20 kg·cm에 1.23° 처진다는 값에서 잡아 멈춤 토크에 비례시켰고, 감쇠와 기어 마찰과 함께 어림이다. 토크가 꺼지면 힘이 없다. 서보를 달지 않은 관절은 거의 잠근다 (힘없이 흔들리면 서보를 단 관절까지 흔들었다). 막대 모델끼리는 겹쳐서 부딪힘을 끈다 (자기 충돌 검사는 실행 전 궤적 검사가 따로 한다). 적분은 implicitfast다.
     - 통합 시험(`crates/controller/tests/sim_loop.rs`): 실행 루프가 시뮬레이션의 J2를 0.6 rad 기울여 버티면 팔의 무게만큼 처지고, 처짐 보정을 켜면 읽는 위치가 목표에 닿는다. 시험은 가상환경의 Python으로 서버를 띄운다 (`uv sync`가 먼저다).
     - 아직 없는 것: 실물의 무게(막대 모델은 실물보다 가볍다), ST-3120의 모델 번호(오면 더한다), 서보의 속도·가속 상한, 시뮬레이션 서보의 보호(과부하, 전압), 실시간 모드의 시험, 메모리 덤프.
  2. IK와 EAIK 대조 시험. 끝났다 (2026-11-14, `crates/controller/src/kinematics.rs`).
     - 정기구학은 설계와 같은 로봇 기술(관절마다 부모 좌표계의 원점과 축, 플랜지 변환)로 한다. IK는 이 팔의 꼴(J1 z, J2·J3·J4 y, J5 z, J6 y, J6 원점이 J5 축 위)을 만들 때 확인하고, 해를 최대 8개(어깨 둘 × 손목 둘 × 팔꿈치 둘) 낸다. J1은 나란한 축 방향의 거리가 일정하다는 식, J5와 J6는 나란한 축의 방향, J2~J4는 평면 두 링크로 푼다.
     - 대조 시험(`crates/controller/tests/ik_eaik.rs`): 설계의 `python -m horilab_design.ik_cases`가 관절 범위 안의 무작위 자세 300개와 EAIK 해를 낸다 (특이 자세 가까이는 뺀다). 자세마다 정기구학이 설계와 같고, 해가 모두 자세에 닿고, 처음 관절 각과 EAIK의 해를 모두 찾고, 해의 수가 같다.
     - 기구학 값은 지금 시험에서 설계 값을 받는다. 로봇 설정에서 읽는 것과 설계와 맞는지 보는 시험은 이동 명령(만드는 순서 3)과 같이 한다.
  3. 궤적(rsruckig)과 이동 명령, 조그.
     - 관절 이동(`crates/controller/src/plan.rs`의 `move_joints`)을 만들었다 (2026-11-14). 저크를 제한하고, 모든 관절이 같이 끝나며, 멈춘 채 시작해 멈춘 채 끝나는 궤적을 rsruckig 3.0.1로 실행 루프의 박자마다 만든다. 시뮬레이션 팔에서 궤적 시간만큼 걸려 목표에 닿는다 (`tests/sim_loop.rs`).
     - 로봇 설정에 기구학(`[kinematics]`: 관절마다 원점과 축, 플랜지)과 관절 이동의 가속·저크 한계(`[run_loop]`, 시험값)를 더했다 (2026-11-14). 기구학은 읽을 때 IK가 푸는 꼴인지 보고, 설계와 같은지는 `tests/test_robot_settings.py`가 본다.
     - 자세로 가기(`plan.rs`의 `move_to_pose`): IK의 해 가운데 관절 한계 안이고 지금 관절 각에 가장 가까운 해를 골라 관절 이동한다. 한계가 ±π를 넘는 관절은 2π 차이 나는 각도 본다 (J4의 80°~235°).
     - 관절 조그(`runloop.rs`의 `jog`)를 만들었다 (2026-11-14). 실행 루프 안의 rsruckig가 속도 제어로 박자마다 지금 위치·속도·가속에서 이어 계산해, 조그 속도가 바뀌어도 매끄럽다. 명령이 0.2초 안에 다시 오지 않으면 멈춘다 (펜던트나 게임패드가 누르는 동안 거듭 보낸다, 0023). 소프트 한계에 다가간 관절은 위치 제어로 바꿔 한계 바로 앞에 세운다: 속도 제어로 세우게 했더니 감속하는 사이 남은 거리가 넉넉해 보여 다시 가속하다 한계를 넘었다. 궤적을 따라가는 중에는 조그하지 않는다.
     - 직교 조그(`runloop.rs`의 `jog_cartesian`)를 만들었다 (2026-11-14). 손끝의 선속도와 각속도(베이스 좌표계)를 박자마다 지금 자세의 야코비안으로 관절 속도로 바꿔 관절 조그와 같은 길로 보낸다 (명령이 끊기면 멈춤, 소프트 한계 앞에 섬, 매끄러움). 특이 자세 가까이에서 관절 속도가 터지지 않게 감쇠 최소 제곱으로 풀고, 관절 속도가 한계를 넘으면 방향을 지킨 채 같은 비율로 줄인다. 손끝 속도 한계는 로봇 설정에 둔다 (시험값 30 mm/s, 20°/s). 플랜지 기준이고, 도구 끝점(TCP) 기준은 도구 설정을 만들 때 더한다.
     - 직선 이동(`plan.rs`의 `move_line`)을 만들었다 (2026-11-14). 플랜지가 곧은 선을 따라가고, 방향은 가장 짧은 회전으로 고르게 바뀐다.
       - IK는 지금 해의 갈래(어깨, 팔꿈치, 손목)에서 이어 푼다 (관절마다 2π 차이 나는 각 가운데 가장 가까운 것). 먼저 0.1 mm(또는 0.1°)마다 길 전체를 풀어, 팔이 닿지 않는 곳, 관절 한계 밖, 한 걸음에 관절이 5° 넘게 바뀌는 곳(해가 끊김, 특이 자세를 지남)이 있으면 거절한다.
       - 시간 매기기(`timing.rs`): 길 위 점마다 빠르기 상한(손끝 속도 한계는 직교 조그와 같은 값, 관절 속도 한계)과 관절 가속 제약을 둔다. 뒤에서 앞으로 끝에서 멈출 수 있는 상한을 훑고, 앞에서 뒤로 그 안에서 가장 빨리 간다 (가속 한계의 95%까지). 저크는 이동 평균 거르개로 제한한다. 폭은 관절 가속이 그 폭 동안 바뀌는 양이 저크 한계의 85% 안에 드는 가장 작은 값이다. 거르면 빠르기가 그 폭 동안 평균되므로, 빠르기 상한을 "그 빠르기로 폭만큼 가는 거리 안의 가장 낮은 상한"으로 미리 깎는다. 멈춘 채 시작해 멈춘 채 끝난다.
       - 박자마다의 관절 각에서 속도·가속·저크를 다시 재어, 한계를 넘으면 전체를 같은 비율로 늦춘다 (안전망).
       - 관절 한계 때문에 늦춰야 하는 곳만 늦춘다. 시험: 팔꿈치가 1.1° 굽은 자세에서 안으로 가는 71 mm 직선은 첫 0.5초를 10 mm/s 아래로 천천히 떠나고, 팔꿈치가 굽은 뒤에는 손끝 한계 가까이 간다. 특이 자세를 지나는 직선은 해가 끊겨 거절한다.
       - 실행 루프는 다른 궤적과 같이 받으면서 속도 한계, 시작 자리, 소프트 한계를 다시 본다.
     - 남은 것: 블렌드 (이어지는 이동의 모서리를 둥글게 잇기, 0023). 프로그램 재생을 만들 때 한다. 원호 이동은 나중이다 (0023).
  4. 메시지와 펜던트 (0023).

## 근거

- 경로 계획을 한 번만 짜면, 시뮬레이션에서 확인한 계획이 실물과 파이에서도 그대로다. PC에 먼저 짜고 다시 옮기면 두 구현이 어긋날 수 있다.
- 팔이 움직이기 전까지 남은 일은 대부분 하드웨어(설계, 출력, 조립)다. 그 사이에 소프트웨어를 실물 없이 만들 수 있으므로, 처음부터 Rust로 짜는 시간이 팔이 처음 움직이는 날을 늦추지 않는다.
- 서보 거래 단위로 붙이면 실물 백엔드에서 실물과 다른 코드는 맨 아래 버스 구현뿐이다 (그 아래 프로토콜은 가짜 서보로 시험한다).

## 영향

- 남는 위험과 막는 법:
  - IK를 직접 짜는 것이 가장 위험하다 (해가 여러 개인 자세, 특이 자세, 관절 한계 처리). EAIK와 많은 자세로 견주는 시험으로 막는다.
  - 시뮬레이션 서보의 처짐과 반응은 실물과 다를 수 있다 (가짜 서보도 맨 서보 확인 뒤에 실물에 맞춰 고쳤다, [0024](0024-servo-bus.md)). 다 만든 팔에서 잰 값으로 맞춘다.
  - 경로 계획을 Rust로 짜는 만큼, 시뮬레이션에서 계획을 처음 시험하는 날은 Python으로 먼저 짤 때보다 늦다. 실물이 오기 전까지 시간이 있어 문제로 보지 않는다.

- 0025의 "팔 움직이기 전에 정할 것" 둘을 이 기록으로 옮겼다. [0007](0007-repo-structure.md)의 컨트롤러 자리에 경로 계획을 더했다 (`packages/sim` 자리는 이미 있다).
- [0023](0023-robot-controller.md)이 만들 때 정하기로 한 것 가운데 경로 시간 매기기, 직교 경로를 따라 IK를 잇는 방법, 특이점 처리를 이 기록에서 정했다.
- [0032](0032-run-loop.md)의 만드는 순서 4(시뮬레이션 백엔드와 메시지)는 이 기록의 만드는 순서로 한다.
