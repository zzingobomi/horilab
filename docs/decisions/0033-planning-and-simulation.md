# 0033. 경로 계획은 컨트롤러 안에 Rust로, 시뮬레이션은 Python MuJoCo 서버를 서보 버스 자리에 붙인다

- 상태: 채택
- 날짜: 2026-11-14

## 배경

- [0025](0025-controller-on-pi.md)는 팔 움직이기 전에 정할 것 둘을 남겼다: 경로 계획(IK, 궤적)을 무엇으로 어디에 짤지, 시뮬레이션 백엔드를 컨트롤러에 붙이는 방법. 조사는 [controller-research.md](../controller-research.md#4-시뮬레이션-연결과-파이용-계획-라이브러리)에 있다.
- 실행 루프의 뼈대, 기준값, 그리퍼는 가짜 서보로 만들었다 ([0032](0032-run-loop.md)). 가짜 서보에는 물리가 없어서 짐에 따른 처짐, 부하, 부딪힘을 시험하지 못한다.
- 설계 패키지에는 해석적 IK(EAIK, `horilab_design.ik`)와 MJCF 만들기(`horilab_design.mjcf`)가 있다.
- 팔은 아직 뽑지 않았다. 팔이 처음 움직이는 날은 출력, 조립, ST-3120 도착이 정한다.

## 검토한 대안

| 정할 것 | 대안 | 판단 |
|---|---|---|
| 경로 계획의 자리 | 팔 움직이기에서는 PC에 Python으로 짜고 PC 없이 쓰기에서 컨트롤러 안에 Rust로 다시 짠다 / 처음부터 컨트롤러 안에 Rust로 짠다 | 처음부터 컨트롤러 안에 Rust로 짠다. IK, 이동 명령, 조그는 컨트롤러의 일이다 ([0023](0023-robot-controller.md)). 한 번만 짜고, 시뮬레이션과 실물, PC와 파이가 같은 계획을 쓰며, 폰과 게임패드의 직교 조그도 처음부터 PC 없이 된다. 더 드는 시간은 팔이 처음 움직이는 날을 늦추지 않는다 (그날은 하드웨어가 정한다) |
| IK | ik-geo 크레이트 / mink / k / 직접 짜기 | 우리 팔의 꼴(J2·J3·J4가 평행)에 맞는 닫힌 해를 직접 짠다 (IK-Geo의 평행 축 셋 풀이). ik-geo 크레이트는 2024년에 멈췄고 LGPL인 NLopt를 cmake로 빌드한다. mink는 컨트롤러에 MuJoCo를 끌고 오고, k는 수치 풀이라 모든 해를 주지 않는다 |
| 궤적 | Ruckig(C++) / rsruckig / TOPP-RA / copp | 조그, 관절 이동, 재생, 관절 공간 블렌드는 rsruckig(순수 Rust, MIT)로 한다. 반지름 블렌드가 있는 직선 이동의 시간 매기기는 직선 이동을 만들 때 재 보고 고른다 (0025) |
| 시뮬레이션 연결 | Rust가 MuJoCo를 직접 부름 / Python 시뮬레이션 서버를 서보 거래 단위로 TCP에 붙임 / Python이 Feetech 바이트를 흉내 냄 | Python 서버를 서보 거래 단위로 붙인다 (조사의 추천). 서보 버스 자리에 인터페이스를 두면, 그 위(관절 층의 ID 대응, 영점·방향 변환, 보호 비트, 통신 실패, 실행 루프)가 실물과 같은 코드로 시험된다. MuJoCo, 설계에서 만든 MJCF, 뷰어, 비전용 카메라 그림은 Python에 그대로 있고 MuJoCo 판은 Python만 맞춘다. Rust에서 MuJoCo를 부르는 크레이트는 판마다 API가 깨졌다. 바이트 흉내는 박자 신호가 따로 필요하고 더 느리며, 프로토콜 코드는 이미 가짜 서보로 시험한다 |

## 결정

- 경로 계획(IK, 이동 명령, 조그, 궤적)은 컨트롤러(`crates/controller`) 안에 Rust로 짠다.
  - IK: J2·J3·J4가 평행인 꼴의 닫힌 해를 직접 짜서 모든 해를 낸다. 관절 축과 링크 길이는 로봇 설정에서 읽는다 ([0009](0009-control-architecture.md)). 맞는지는 설계 패키지의 EAIK로 만든 자세와 해의 목록과 견주어 본다.
  - 궤적: rsruckig.
- 시뮬레이션: Python MuJoCo 시뮬레이션 서버(`packages/sim`)를 TCP로 붙인다.
  - 컨트롤러의 서보 버스 자리에 인터페이스(서보 거래: 핑, 읽기, 동기 읽기, 쓰기, 동기 쓰기)를 두고, 실물(Feetech 버스)과 시뮬레이션 두 구현을 둔다. 가짜 서보는 Feetech 버스 쪽 시험에 그대로 쓴다.
  - 한 걸음씩 간다 (PX4의 lockstep): 박자마다 동기 읽기가 오면 시뮬레이션이 한 주기만큼 물리를 진행하고 상태로 답한다. 실행 루프는 시뮬레이션 시간을 시계로 쓴다. 시험용 빠른 모드와 뷰어·펜던트용 실시간 모드를 둔다.
  - 시뮬레이션 서보는 실물 서보의 레지스터(토크 스위치, 목표, 토크 한도, 위치, 속도, 부하, 전압, 온도, 상태 바이트)를 같은 단위로 낸다. 위치 서보가 짐에 처지는 것과 토크 한도는 MuJoCo의 위치 액추에이터와 힘 한계로 흉내 내고, 게인은 다 만든 팔에서 잰 처짐에 맞춘다.
  - 같은 TCP로 파이의 컨트롤러를 PC의 시뮬레이션에 붙일 수 있다.
- 만드는 순서:
  1. 서보 버스 인터페이스와 시뮬레이션 서버. 실행 루프를 시뮬레이션으로 시험한다.
     - 서보 버스 인터페이스(`ServoBus`, `crates/servo/src/feetech/bus.rs`)를 두었다 (2026-11-14). 관절 층과 실행 루프는 이 거래만 쓰고, Feetech 버스(실물과 가짜 서보)가 그것을 낸다. 시뮬레이션 서버와 그 구현이 남았다.
  2. IK와 EAIK 대조 시험.
  3. 궤적(rsruckig)과 이동 명령, 조그.
  4. 메시지와 펜던트 (0023).

## 근거

- 경로 계획을 한 번만 짜면, 시뮬레이션에서 확인한 계획이 실물과 파이에서도 그대로다. PC에 먼저 짜고 다시 옮기면 두 구현이 어긋날 수 있다.
- 팔이 움직이기 전까지 남은 일은 대부분 하드웨어(설계, 출력, 조립)다. 그 사이에 소프트웨어를 실물 없이 만들 수 있으므로, 처음부터 Rust로 짜는 시간이 팔이 처음 움직이는 날을 늦추지 않는다.
- 서보 거래 단위로 붙이면 실물 백엔드에서 실물과 다른 코드는 맨 아래 버스 구현뿐이다 (그 아래 프로토콜은 가짜 서보로 시험한다).

## 영향

- 남는 위험과 막는 법:
  - IK를 직접 짜는 것이 가장 위험하다 (해가 여러 개인 자세, 특이 자세, 관절 한계 처리). EAIK와 많은 자세로 견주는 시험으로 막는다.
  - 시뮬레이션 서보의 처짐과 반응은 실물과 다를 수 있다 (가짜 서보도 맨 서보 확인 뒤에 실물에 맞춰 고쳤다, [0024](0024-servo-bus.md)). 다 만든 팔에서 잰 값으로 맞춘다.
  - 경로 계획을 Rust로 짜는 만큼, 시뮬레이션에서 계획을 처음 시험하는 날은 Python으로 먼저 짤 때보다 늦다. 실물이 오기 전까지 시간이 있어 문제로 보지 않는다.

- 0025의 "팔 움직이기 전에 정할 것" 둘을 이 기록으로 옮겼다. [0007](0007-repo-structure.md)의 컨트롤러 자리에 경로 계획을 더했다 (`packages/sim` 자리는 이미 있다).
- [0032](0032-run-loop.md)의 만드는 순서 4(시뮬레이션 백엔드와 메시지)는 이 기록의 만드는 순서로 한다.
