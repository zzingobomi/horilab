# 0009. 제어 구조: 모터 프로세스와 안전

- 상태: 채택
- 날짜: 2026-11-07

## 배경

- 실물과 시뮬레이션을 같은 제어 코드로 움직인다 ([0001](0001-inherited-decisions.md)). 그러려면 제어 코드와, 서보나 MuJoCo를 실제로 움직이는 코드 사이의 경계를 정해야 한다.
- 모터 제어는 영상 처리와 다른 프로세스에서 돌고, PC와 파이 어디서든 같은 코드로 돌아야 한다 ([0005](0005-connection-architecture.md)).
- 서보는 위치 제어 서보다. 목표 위치를 주면 서보 안에서 위치를 맞춘다. 7개를 한 버스에서 동기 쓰기·읽기로 다룬다.
- 실물은 사람을 다치게 하거나 스스로 부서질 수 있다. 안전 기능은 나중에 덧붙이면 빠지는 곳이 생기므로 구조를 정할 때 자리를 정한다. 전원 차단 같은 물리적인 안전 규칙은 [hardware.md](../hardware.md#안전)에 있다.

## 검토한 대안

### 시뮬레이션과 실물을 바꿔 끼우는 자리

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 한 프로세스 안에서, 로봇 인터페이스 하나에 시뮬레이션 구현과 실물 구현을 둔다 | 가장 단순하다 | 서보 명령 주기가 같은 프로세스의 IK·계획 계산에 밀릴 수 있다. 모터 제어를 파이로 옮기려면 결국 프로세스를 나눠야 한다 |
| B. 모터 프로세스를 따로 두고, 상위 코드는 메시지로만 명령한다. 시뮬레이션과 실물은 모터 프로세스 안의 백엔드만 다르다 | 서보 명령 주기가 상위 코드와 상관없다. 같은 메시지가 PC 안에서도, 네트워크 너머 파이로도 간다. 안전 검사를 한곳에 모은다 | 메시지 형식을 정해야 하고 프로세스가 둘이다 |

### 상위 코드가 보내는 명령

| 대안 | 장점 | 단점 |
|---|---|---|
| 관절 목표를 주기마다 보낸다 (스트리밍) | 모터 프로세스가 단순하다 | 상위 코드나 네트워크가 늦으면 움직임이 끊긴다. 프로세스를 나눈 의미가 줄어든다 |
| 시간이 붙은 관절 궤적을 통째로 보낸다 | 모터 프로세스가 일정한 주기로 실행해서 상위 코드가 늦어도 움직임이 매끄럽다. 실행 전에 궤적 전체를 검사할 수 있다 | 궤적 형식과 실행 중 교체·정지 규칙을 정해야 한다 |
| 목표 자세만 보내고 서보가 알아서 간다 | 가장 단순하다 | 관절이 따로 움직여서 직선 이동 같은 협조 동작을 못 한다 |

## 결정

B로 하고, 명령은 시간이 붙은 관절 궤적이다.

```
[상위 제어: 작업, IK, 궤적]              시뮬레이션이든 실물이든 같은 코드
     │  명령: 궤적, 정지, 토크 켜기·끄기
     │  상태: 관절 위치, 부하, 온도, 전압, 오류
     ▼  (pyzmq. PC 안에서도, 파이로도)
[모터 프로세스: 실행 루프 + 안전 검사]     같은 코드
     ├─ 실물 백엔드: Feetech 서보 (동기 쓰기·읽기)
     └─ 시뮬레이션 백엔드: MuJoCo (PC에서만)
```

- 상위 제어는 모터 프로세스하고만 이야기하고, 상대가 시뮬레이션인지 실물인지 모른다. 실물 백엔드는 명시적으로 켰을 때만 쓴다 ([0005](0005-connection-architecture.md)).
- 모터 프로세스가 일정한 주기로 궤적을 따라 서보 목표를 보낸다. 조그처럼 바로바로 움직이는 동작은 짧은 궤적을 이어 보낸다.
- 관절은 번호가 아니라 이름으로 부른다 (MJCF와 같은 이름). 메시지와 코드 안의 단위는 rad와 s다. 서보 값(0~4095)과 rad 사이 변환(방향, 영점)은 실물 백엔드 안에서만 한다.
- 모터 프로세스는 data/의 로봇 설정만 읽는다 (서보 ID·방향·영점, 소프트웨어 관절 한계, 속도 한계, 경고 기준). 설계 패키지, MuJoCo, 생성된 MJCF가 필요 없어서 파이에서도 그대로 돈다. 로봇 설정의 관절 이름이 MJCF와 같은지, 소프트웨어 관절 한계가 설계의 기계적 범위 안에 있는지는 PC의 테스트로 확인한다.
- 실행 루프와 안전 검사는 motor 패키지에 있다. 시뮬레이션 백엔드는 control 패키지에 두고 이 실행 루프에 끼워 쓴다. 그래서 시뮬레이션에서도 실물과 같은 실행 루프와 안전 검사를 거친다 ([0007](0007-repo-structure.md)).
- 실행 루프의 주기는 서보 7개로 잰 통신 시간을 보고 정한다 ([0008](0008-environment-and-packages.md)).

### 안전

안전 검사는 모터 프로세스에 둔다. 상위 제어도 계획할 때 미리 거르지만, 마지막 판단은 모터 프로세스가 한다. 서보로 가는 명령은 모두 여기를 지난다.

| 상황 | 처리 |
|---|---|
| 시작, 재연결 | 서보의 현재 위치를 읽고 목표를 현재 위치로 맞춘 뒤 토크를 켠다. 현재 위치에서 시작하는 궤적만 받는다. 끊기기 전의 궤적은 이어서 실행하지 않는다 |
| 관절·속도 한계 | 한계를 넘는 궤적은 실행 전에 통째로 거부한다. 잘라서 실행하지 않는다 |
| 상위 제어가 죽거나 끊김 | 이미 검사한 궤적을 끝내고 그 자리에서 버틴다. 조그는 짧은 궤적이라 곧 멈춘다 |
| 서보 통신 오류 | 읽기·쓰기 실패가 정해진 횟수를 넘으면 새 목표를 보내지 않고 오류 상태가 된다. 사람이 확인하고 풀기 전에는 움직이지 않는다 |
| 과부하, 과열, 전압 이상 | 부하·온도·전압을 주기적으로 읽고, 기준을 넘으면 멈추고 버틴 채 알린다. 토크를 끄면 팔이 떨어지므로 바로 끄지는 않는다. 서보 자체의 보호 설정(최대 토크 등)도 서보 준비 때 맞춘다 |
| 정지 | 소프트웨어 정지(멈추고 버티기)는 명령 하나로 한다. 최종 수단은 서보 전원 차단이다 ([hardware.md](../hardware.md#안전)). 전원과 로봇 사이의 스위치는 서보 전원 분배와 같이 정한다 |
| PC와 서보 사이 통신이 끊김 | 소프트웨어로는 손쓸 수 없다. 위치 서보라 마지막 목표를 계속 잡고 있을 것으로 보고, 전원 차단으로 대응한다. 서보에 통신 감시 기능이 있는지는 레지스터 표로, 끊겼을 때 실제로 어떻게 되는지는 서보 준비 때 실물로 확인한다 |

- 기준값(한계, 실패 횟수, 부하·온도·전압 기준)은 로봇 설정에 두고, 서보와 연결 준비 단계(제작 로드맵 2단계)에서 정한다.

### 실물을 처음 움직이기 전에 통과할 시험

1. 시뮬레이션 백엔드로 상위 제어를 돌려 궤적 실행, 정지, 한계 거부를 확인한다 (자동 테스트).
2. 실물 백엔드의 오류 처리를 가짜 서보 버스로 시험한다 (응답 없음, 이상한 값).
3. 서보 7개를 연결해 한 주기(동기 쓰기 + 상태 동기 읽기)에 걸리는 시간과 흔들림을 잰다. 이 값으로 실행 루프 주기를 정한다.
4. [0005](0005-connection-architecture.md)의 부하 시험: PC에서 영상 처리를 돌린 채 몇 시간 동안 명령 간격과 통신 오류를 기록한다.
5. 실물 첫 동작은 관절 하나, 낮은 토크 제한, 느린 속도로 시작한다.

## 근거

- 모터 프로세스를 경계로 두면 0005의 두 요구(영상 처리와 다른 프로세스, PC와 파이 어디서든)와 "같은 코드로 시뮬레이션과 실물"을 한 구조로 만족한다.
- 궤적을 통째로 보내면 상위 코드나 네트워크가 늦어도 움직임이 일정하다. ROS의 joint_trajectory_controller도 궤적을 받아 제어기 안에서 보간한다.
- 안전 검사를 서보 바로 앞 한곳에 두면, 상위 코드의 버그나 시험 스크립트가 보낸 명령도 빠짐없이 검사된다. 시뮬레이션도 같은 검사를 거치므로 안전 기능을 실물 없이 시험할 수 있다.
- 한계를 넘는 궤적을 자르지 않고 거부하는 건, 잘린 궤적은 계획한 것과 다른 움직임이 되기 때문이다.

## 영향

- motor 패키지가 생긴다 ([0007](0007-repo-structure.md)).
- 메시지 형식과 궤적 형식(보간 방법, 실행 중 교체 규칙)은 서보와 연결 준비 단계에서 정한다.
- 상위 제어가 죽어도 궤적은 끝까지 간다. 긴 궤적에서 이게 문제가 되면, 상위 제어의 생존 신호가 끊길 때 멈추는 규칙을 더한다.
