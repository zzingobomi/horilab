# 0006. 아키텍처: 값의 형식과 생성 흐름

- 상태: 채택
- 날짜: 2026-11-07

## 배경

- 같은 치수 값에서 출력 부품, 조립 화면, URDF, MJCF, 부품표, 토크·오차 계산을 뽑는다 ([0001](0001-inherited-decisions.md)).
- 모터 제어는 PC와 파이 어디서든 같은 코드로 돌 수 있어야 하고, 실물과 시뮬레이션을 같은 코드로 움직인다 ([0005](0005-connection-architecture.md)).
- 값은 성격이 다른 네 종류다.
  - 설계로 정하는 값 (명목 치수, 서보 종류, 손목 형식, 출력 설정)
  - 실물을 재서 얻는 값 (공차, 서보 실측 치수·무게, 출력물 무게, 처짐·백래시)
  - 조립한 로봇마다 맞추는 값 (서보 ID·방향·영점, 캘리브레이션 결과)
  - 구매 데이터 (부품표의 주문 상태와 가격, [0002](0002-docs-system.md))
- 실물은 모델과 어긋난다. 출력하면 구멍이 작게 나오고, 조립할 때마다 관절 영점이 조금씩 다르고, 서보는 처지고 백래시가 있다. 이 차이를 어디서 다룰지 정하지 않으면 시뮬레이션과 실물이 따로 논다.
- 조사로 확인한 사실 (2026-11):
  - build123d는 MJCF와 URDF를 내보내지 않는다. 질량 특성은 밀도 1 기준이라 밀도를 곱해야 한다.
  - MuJoCo의 MjSpec은 코드로 모델을 만들고 XML로 저장하며, 그리퍼 같은 하위 모델을 사이트에 붙일 수 있다. 3.2.5부터 일반 사용 권장이지만 가끔 바뀐다.
  - URDF는 직접 써야 한다. URDF를 MJCF로 바꾸면 사이트·액추에이터·센서가 없고, 기본 설정에서는 고정 링크(플랜지, TCP)가 부모에 합쳐진다 (설정으로 끌 수 있다).
  - MuJoCo는 메시 충돌을 볼록 껍질로 계산해서 오목한 부품은 틀린다.
  - Python 표준 라이브러리의 tomllib는 TOML을 읽기만 하고 쓰지 못한다.

## 검토한 대안

### 값을 둘 형식

| 대안 | 장점 | 단점 |
|---|---|---|
| Python 코드 (dataclass) | 읽는 과정이 없고, 타입과 파생 값이 한곳에 있다 | 값과 코드가 섞인다. 측정 스크립트가 값을 갱신하기 어렵다 |
| TOML 파일 + Python 스키마 | 값과 코드가 분리되고 주석을 쓸 수 있다. 표준 라이브러리로 읽는다. 바뀐 내용이 깔끔하게 보인다 | 스키마와 파일 양쪽에 이름이 있다 |
| YAML 파일 + 스키마 | 중첩 표현이 편하다 | `no`가 false로 읽히는 식의 암묵 변환 함정이 있고 라이브러리가 더 필요하다 |

### 실측 값을 반영하는 방법

| 대안 | 장점 | 단점 |
|---|---|---|
| 잰 값으로 설계 값을 고친다 | 파일이 하나라 단순하다 | 명목값이 사라진다. 로봇 한 대의 조립 오차가 설계에 섞여 다음 출력에까지 들어간다 |
| 설계 값은 그대로 두고, 차이의 종류마다 정해진 곳에서 보정한다 | 출력 보정, 로봇별 보정, 시뮬레이션 맞춤이 섞이지 않는다. 값이 어디서 왔는지 보인다 | 규칙을 알고 지켜야 한다 |

### URDF와 MJCF를 만드는 방법

| 대안 | 장점 | 단점 |
|---|---|---|
| URDF를 만들고 MuJoCo로 MJCF 변환 | 작성기가 하나다 | MJCF 전용 요소를 따로 덧붙여야 하고, 기본 설정에서 고정 링크가 합쳐진다 |
| 로봇 기술 하나에서 URDF 작성기와 MJCF 작성기를 따로 | 각 형식의 기능을 다 쓴다. 둘을 서로 대조해 검사할 수 있다 | 작성기가 둘이다 |

### 출력 부품의 질량

| 대안 | 장점 | 단점 |
|---|---|---|
| CAD 부피 × 필라멘트 밀도 | 가장 간단하다 | 속이 꽉 찬 것으로 계산돼 실제보다 무겁다 |
| 출력 설정으로 근사 (겉은 꽉 차게, 안쪽은 채움 비율만큼) | 출력하기 전에 코드에서 바로 나온다 | 근사라서 오차가 남는다 |
| 슬라이서가 계산한 무게 | 출력 설정을 정확히 반영한다 | 부품마다 슬라이스해서 값을 손으로 옮겨야 한다 |
| 출력물을 저울로 잰다 | 가장 정확하다 | 출력한 뒤에야 안다 |

### 충돌 형상

| 대안 | 장점 | 단점 |
|---|---|---|
| CAD 메시 그대로 | 손이 덜 간다 | 볼록 껍질로 계산돼 오목한 부품은 틀리고 느리다 |
| 볼록 분해 (CoACD) | 모양을 잘 따라간다 | 도구가 하나 더 들고 결과가 들쭉날쭉하다 |
| 치수 값에서 만든 기본 도형 (상자, 원기둥, 캡슐) | 빠르고 접촉이 안정적이다. 치수 값에서 바로 나온다 | 모양을 대략으로만 따른다. 크기를 잘못 잡으면 튀어나온 볼트 머리나 브래킷의 충돌을 놓친다 |

### 생성물 관리

| 대안 | 장점 | 단점 |
|---|---|---|
| 생성물을 git에 커밋 | 코드를 돌리지 않아도 바로 본다 | 코드와 어긋날 수 있다. 출력 파일은 크고 바이너리다 |
| 커밋하지 않고 필요할 때 만든다 | 늘 코드와 맞는다 | 보려면 명령을 돌려야 한다 |

## 결정

**값의 형식**

- 값 파일은 모두 TOML이고, 읽을 때 스키마(pydantic)로 검사한다. 파생 치수는 파일에 쓰지 않고 코드에서 계산한다.
- 파일은 위의 네 종류별로 나눈다. 실측 값이 바뀌어도 설계 값 파일은 그대로고, 로봇마다 다른 캘리브레이션이 설계와 섞이지 않는다.
- 사람이 보는 파일의 단위는 mm와 도(°)이고, 키 이름에 단위를 붙인다 (예: `upper_arm_mm`, `range_deg`). 코드 안의 로봇 기술은 SI(m, rad)로 바꿔 들고 있는다. 세부 단위 규칙은 코드 규칙(기반 결정 6번)에서 정한다.
- 읽기는 tomllib로 한다. 스크립트가 값을 쓸 때(실측 기록, 영점 맞추기)는 tomlkit으로 써서 손으로 단 주석과 순서를 지킨다.

**명목 모델과 실물의 차이**

설계 값은 명목값이고, 잰 값으로 덮어쓰지 않는다. 차이는 종류에 따라 다른 곳에서 다룬다.

| 차이 | 예 | 값을 두는 곳 | 다루는 방법 |
|---|---|---|---|
| 출력할 때마다 똑같이 생기는 차이 | 구멍이 작게 나옴, 서보 실측 치수 | 실측 값 | 부품 형상을 보정해서 다음 출력부터 실물을 모델에 맞춘다. 관절 축 위치와 링크 길이 같은 기구학 값은 바꾸지 않는다 |
| 조립한 로봇마다 다른 차이 | 관절 영점, 조립 오차 | 로봇 설정·캘리브레이션 | 실물을 움직일 때만 적용한다. 처음에는 관절 영점과 방향만 맞춘다 (마스터링 핀, [design.md](../design.md#정밀도-대책)). 링크 길이 같은 기구학 보정은 재 보고 필요할 때 보정 값으로 따로 두고, 생성기가 명목 모델과 별도로 보정 모델을 만든다 |
| 움직임의 차이 | 처짐, 백래시, 서보 응답 | 실측 값 | 실물에서 잰 값으로 MJCF의 관절·액추에이터 파라미터를 맞춘다 |

- 설계 검증(토크, 작업 범위, 충돌)은 명목 모델로 한다.
- 실물이 모델과 얼마나 맞는지 재는 방법은 정밀도 기준과 같이 정한다 ([status.md](../status.md#남은-질문)).

**생성 흐름**

```
설계 값 + 실측 값 (TOML)
  → 검사, 파생 값 계산
  → 로봇 기술: 링크, 관절 축과 원점, 관절 한계 (SI 단위)
  → 부품과 조립 (build123d): 부품마다 색 그룹, 출력 방향, 쓰는 볼트·너트·베어링
  → 질량 특성: 아래 "질량" 규칙
  → 내보내기
      · 출력 파일: 부품별 3MF/STL, 출력 방향으로 놓고 색 그룹별로 묶음
      · URDF: 표준 라이브러리 XML로 직접 작성
      · MJCF: MjSpec으로 작성. 그리퍼는 따로 만들어 플랜지 사이트에 붙임
      · 설계 부품표 (볼트·너트·베어링 개수) → 구매 데이터와 합쳐 docs/bom.md
      · GLB: 웹 화면이 필요해지면
  → 검사: 토크 여유(정격 토크 기준), 백래시 오차, 출력 범위,
          모델 사이 FK 일치, 충돌 형상이 부품을 감싸는지,
          작업 범위·IK·특이점·충돌(MuJoCo)
```

**질량**

- 출력 전: 무게 = 필라멘트 밀도 × (겉 부피 + 안쪽 부피 × 채움 비율). 겉 부피는 겉넓이 × 벽 두께로 근사한다. 밀도, 벽 두께, 채움 비율은 설계 값(출력 설정)이다.
- 출력 후: 저울로 잰 무게가 실측 값에 있으면 그 값을 쓴다.
- 무게중심과 관성은 CAD 형상을 고른 밀도로 보고 계산한 뒤, 위의 무게에 비례시킨다.
- 서보는 실측 무게를, 베어링·볼트·너트는 규격 값을 더한다.

**충돌 형상**

- 충돌 형상은 치수 값에서 만든 기본 도형이다. 볼트 머리나 브래킷처럼 튀어나온 부분까지 감싸는 크기로 만든다.
- CAD 부품이 그 링크의 충돌 형상 안에 들어가는지 테스트로 확인한다. 부품을 키우고 충돌 형상을 그대로 두면 테스트가 실패한다.
- 감싸면 지나치게 커지는 부품은 그 부품만 메시 충돌을 쓸 수 있다. 볼록 껍질로 계산되므로 볼록한 부품에만 쓴다.
- 보이는 모양은 CAD 메시를 쓴다. 메시는 출력 방향이 아니라 링크 좌표계로 내보낸다.
- IK와 경로 계획에서 둘 최소 거리는 골격 설계 때 정한다.

**그 밖**

- 제어 코드는 설계 코드(build123d)를 불러오지 않는다. 경로 계획과 시뮬레이션은 생성된 MJCF와 로봇 설정을 읽고, 컨트롤러는 로봇 설정만 읽는다 ([0009](0009-control-architecture.md)). 그래서 컨트롤러는 생성물 없이 파이에서도 돈다.
- 생성물은 `build/`에 만들고 git에 넣지 않는다. 예외는 docs/bom.md 하나다. 문서라서 커밋하고, 데이터와 맞는지 테스트로 확인한다.
- MJCF, URDF, 설계 값에서 직접 계산한 FK를 영점과 무작위 자세 여러 개에서 비교하는 테스트를 둔다. 축이 뒤집혀도 영점에서는 같아 보이기 때문이다.

## 근거

- TOML은 값과 코드를 나누고 주석을 쓸 수 있으며, Python 표준 라이브러리로 읽는다. YAML의 암묵 변환 함정이 없다. 쓰기는 tomlkit이 주석을 지켜 준다.
- 설계 값을 명목값으로 지키면 출력 공정의 차이, 로봇마다의 차이, 움직임의 차이가 섞이지 않아서, 실물과 모델이 어긋났을 때 원인을 찾기 쉽다. 출력 공정의 차이는 모델을 실물에 맞추지 않고 실물을 모델에 맞춘다. 그래야 모든 출력물과 생성물이 같은 명목 모델을 따른다.
- 작성기를 둘로 두면 MJCF 전용 기능(사이트, 액추에이터, 그리퍼 붙이기)을 다 쓰고, URDF와 MJCF를 서로 대조해 축 방향 같은 실수를 잡을 수 있다.
- 질량은 출력 전에도 토크 계산에 필요하다. 출력 전 값은 설계 판단용이라 근사로 시작하고, 출력한 뒤에는 저울 값으로 바꾼다. 슬라이서 값은 부품마다 손으로 옮겨야 해서 쓰지 않는다.
- 기본 도형 충돌은 빠르고 안정적이며 치수 값에서 바로 나온다. 감싸는 크기로 만들고 테스트로 확인하면 놓치는 충돌을 막는다.
- 생성물을 커밋하지 않으면 코드와 어긋날 일이 없다.

## 영향

- 필요한 패키지와 버전은 [0008](0008-environment-and-packages.md)에 있다 (tomlkit 포함).
- 단위 변환 위치와 좌표계 규칙은 코드 규칙(6번)에서 정한다.
- IK는 로봇 기술의 관절 축과 원점에서 바로 만든다 ([0008](0008-environment-and-packages.md)).
- 기구학 보정이 필요해지면 보정 값의 형식과 보정 모델을 만드는 방법을 그때 정한다.
