# 0024. 서보 버스: 서보와 이야기하는 맨 아래층

- 상태: 채택
- 날짜: 2026-11-10

## 배경

- 2단계(서보 준비: ID, EEPROM 확인·설정, 통신 시간)와 팔을 처음 움직이기 전의 맨 서보 확인([0028](0028-ur-style-joints.md))에 서보와 이야기하는 프로그램이 필요하다. [0009](0009-control-architecture.md)의 실물 백엔드 맨 아래층이고, 나중에 컨트롤러의 실행 루프와 API([0023](0023-robot-controller.md))가 이 위에 올라간다. 어느 길로 오든 실물 서보에 닿는 코드는 이 층 하나다.
- 컨트롤러는 Rust로 짜고 로봇 옆 컨트롤러 파이에서 돌린다 ([0025](0025-controller-on-pi.md)). 그래서 이 층도 Rust다. 처음에는 Feetech 공식 SDK(ftservo-python-sdk, [0008](0008-environment-and-packages.md)) 위에 Python으로 짰고, 그것은 기준 구현으로 남긴다.
- SDK(PyPI 최신 2.0.1)의 소스에서 본 것 (2026-11-10). Rust로 직접 짤 때 같은 함정을 피한다:
  - 레지스터 상수가 일부뿐이다. 게인, 보호 설정, 상태 바이트가 없다. 주소로는 어떤 레지스터든 읽고 쓸 수 있다.
  - 동기 읽기 도우미(GroupSyncRead)는 응답이 한 패킷보다 짧으면 지난 주기 값을 그대로 돌려준다. 이를 막는 검사가 주석 처리돼 있다.
  - 스레드 안전이 없고, 통신 도중 예외(USB가 빠짐 등)가 나면 '사용 중' 표시가 남아 그 뒤 모든 통신이 실패한다.
  - EEPROM 쓰기를 잠금으로 감싸지 않고, 부하의 방향 비트를 풀지 않는다.
  - 응답이 없으면 고정 여유(50 ms)를 `time.time()`으로 재며 쉬지 않고 기다린다. Windows의 Python 3.12에서 `time.time()`은 약 15.6 ms 단위다.
- 메모리 표는 Waveshare 문서([hardware.md](../hardware.md#서보-사양))를 따른다.
  - 잠금(55)은 EEPROM에 쓴 값이 전원을 꺼도 남는지만 정한다. 잠근 채 쓴 값도 바로 적용되고, 전원을 끄면 사라진다.
  - 토크 스위치(40)에 128을 쓰면 현재 위치를 2048로 다시 잡으며 위치 오프셋(EEPROM)을 바꾼다.
  - 각도 한계(9~12)가 있으면 서보는 그 안에서만 움직인다.
- 공식 SDK에는 공장 초기화 명령이 없다. 명령은 PING, READ, WRITE, REG_WRITE, ACTION, SYNC_READ, SYNC_WRITE뿐이다 (2026-11-11 확인). 서보 펌웨어가 따로 지원하는지는 모른다.
- 이전 프로젝트의 사실: 가진 STS 서보 일곱 개(STS3215 여섯, STS3250 하나)는 그 SO-101에서 한 버스로 쓰던 것이라 공장값이 아니다. 그때 어떤 도구로 무엇을 썼는지는 모른다 (LeRobot으로 세팅했다면 바뀌는 값은 [hardware.md](../hardware.md#서보-설정-주의)와 [controller-research.md](../controller-research.md#feetech-서보를-다루는-코드)). 이전 프로젝트의 코드는 EEPROM을 읽거나 쓴 적이 없고, 온도·전압·전류·상태를 읽지 않았고, 서보 상태를 파일로 남기지 않았다. 모터 설정 파일에는 PID를 비워 두고 Feetech 기본값을 쓴다고 적혀 있다. 동기 읽기 실패가 로그에 두 번 있다. 그래서 지금 서보들에 무엇이 들어 있는지 모른다.

## 검토한 대안

| 정할 것 | 대안 | 판단 |
|---|---|---|
| 서보 프로토콜 | 공식 Python SDK를 보완해 쓰기 / Rust 서보 라이브러리(rustypot) 쓰기 / Rust로 직접 짜기 | Rust로 직접 짠다. 컨트롤러가 Rust라서다 (0025). rustypot 1.13.1을 아래 버스 요구로 평가했다 (2026-11-11). 응답마다 길이·체크섬·ID를 확인해서 지난 값은 돌려주지 않지만, 동기 읽기는 서보 하나만 실패해도 통째로 실패해 다른 서보의 값까지 잃는다. 위층 버스는 잠금을 LeRobot식(토크를 따라감)으로 다뤄 아래 EEPROM 절차와 다르고, 시험용 가짜 포트는 라이브러리 밖에서 쓸 수 없고, 라이브러리인데 clap·env_logger 같은 의존성을 끌고 오고, STS3250과 ST-3120 표가 없다. 그래서 참고만 했다: 응답 확인, 보내기 전에 받은 바이트 버리기, 부호 비트 배치(우리 표와 같다). 프로토콜은 작고(패킷마다 머리, ID, 길이, 명령, 값, 체크섬) 세부를 다 파악했다 ([controller-research.md](../controller-research.md#feetech-서보를-다루는-코드)) |
| 동기 읽기 | 받은 바이트를 한 덩어리로 보기 / 서보마다 나눠 확인하기 | 서보마다 나눈다. 지난 값을 새 값처럼 받으면 응답 없는 서보가 멀쩡해 보이고, 0009의 통신 오류 처리(연속 실패를 세어 멈춤)가 듣지 않는다 |
| 영점 | 혼 톱니로 조립 자리를 맞추고 소프트웨어 영점 / 영점 핀 자리에서 위치 오프셋을 구워 0/4095 경계를 옮기고 소프트웨어 영점 / 토크 스위치 128 | 위치 오프셋으로 경계를 옮기고, 변환은 소프트웨어 영점으로 한다 (2026-11-14, 아래 영점). 처음에는 EEPROM을 덜 쓰려고 오프셋을 0으로 두고 조립 자리를 맞추려 했다. 관절 범위가 양쪽 160°에 기계 멈춤이 163°라 경계를 둘 자리가 범위 반대편의 34°뿐이어서 혼 톱니(한 칸 14.4°)로는 맞추기 어렵다. 128은 지금 자리를 2048로만 잡아 핀 자리가 범위 가운데가 아닌 관절에 맞지 않고, 잠금 절차 밖에서 EEPROM을 쓴다. 변환을 관절 층에서만 하는 것(0009)은 그대로다 |
| 맨 서보 확인 프로그램 | 실행 루프와 메시지를 먼저 만들기 / 확인과 기록을 하는 명령 하나 | 명령 하나. 짧은 확인만 해서 궤적과 메시지가 필요 없다. 메시지 형식은 0023을 정한 뒤다 |
| 기록 형식 | CSV / Parquet / JSON Lines | CSV와 JSON 메타. 돌리는 중에 이어 쓰고, 중간에 꺼져도 앞부분이 남고, 어디서든 바로 읽힌다. 30분을 초당 20번 기록해도 수 MB다 |

## 결정

```
crates/servo (Rust, 라이브러리)
├─ feetech/registers  메모리 표: 이름, 주소, 크기, EEPROM/RAM, 읽기 전용, 부호 표현, 단위
├─ feetech/packet     패킷 만들기와 응답 나누기 (길이, 체크섬)
├─ feetech/bus        서보 버스: 읽기·쓰기, 동기 읽기·쓰기, EEPROM 절차. 서보 ID와 raw 값만 안다
├─ feetech/fake       가짜 서보 버스: 포트 자리에 끼워 프로토콜 코드까지 시험한다
└─ sim                시뮬레이션 버스: 같은 서보 거래를 시뮬레이션 서버에 TCP로 보낸다 (0033)

crates/controller (Rust, 실행 파일)
├─ settings           로봇 설정 (data/robot.toml)
├─ joints             관절 층: 관절 이름·rad와 ID·raw 사이 변환, 안전 검사. 맨 서보는 raw 그대로
├─ prepare            값 적용: EEPROM을 로봇 설정에 맞춘다
├─ record             기록
├─ check              맨 서보 확인
├─ runloop            실행 루프 (0032)
├─ kinematics, plan, timing   경로 계획: IK, 관절 이동, 직선 이동 (0033)
└─ (명령)              settings, ports, apply, check, check-state

packages/servo/src/horilab_servo/feetech (Python)   같은 설계의 기준 구현 (공식 SDK 위)
```

- 서보 버스가 하는 일:
  - 레지스터를 이름으로 읽고 쓰고 부호를 푼다. 모든 레지스터는 메모리 표 한 곳에서 온다.
  - 동기 읽기 응답을 서보마다 나눠 길이와 체크섬을 확인한다. 응답이 없거나 깨진 서보는 서보마다 그 오류를 돌려주고, 지난 값은 돌려주지 않는다.
  - 포트는 버스 하나만 쓴다. 통신 도중 오류가 나도 다음 통신이 막히지 않는다.
  - 서보마다 통신 성적(성공, 응답 없음, 깨짐, 연속 실패)을 센다.
  - 응답을 기다리는 여유를 정할 수 있고, 단조 시계로 잰다. 기다리는 동안 CPU를 쓰지 않는다.
- EEPROM은 세 길로만 쓴다. EEPROM 쓰기와 ID 바꾸기는 쓰기 전후의 메모리 덤프를 기록한다.
  - EEPROM 쓰기: 토크가 꺼져 있을 때만, 잠금 풀기 → 쓰기 → 잠그기 → 다시 읽어 확인. 도중에 실패해도 다시 잠근다.
  - ID 바꾸기: 버스에 서보가 하나만 물렸을 때, 새 ID가 이미 응답하면 하지 않는다.
  - 잠근 채 바꿔 보기(`write_trial`): 잠금을 건 채 쓴다. 잠금이 풀려 있으면 먼저 잠근다. 바로 듣고, 전원을 끄면 사라진다. 토크가 켜져 있어도 된다. 로봇 관절에는 P·I·D와 응답 지연(7번)만 쓴다 (팔에서 게인을 고를 때, 통신 시간을 잴 때). 맨 서보 확인은 각도 한계, 전압 하한, 힘을 빼는 조건(19), 위치 오프셋(31), 과부하 보호 설정(34~36)도 잠깐 바꿨다가 되돌린다. 버스는 이 레지스터들만 받고, 관절 층은 한계와 보호 설정을 맨 서보에만 허락한다. 바꾼 값은 기록에 남기고, 고른 값은 EEPROM 쓰기로 굽는다.
  - 통신 속도는 바꾸지 않는다 (1 Mbps). 토크 스위치의 128과 잠금 직접 쓰기는 막는다.
- 서보 ID는 관절 번호와 같다: J1 1, J2 2(ST-3120), J3 3(STS3250), J4~J6 4~6. 그리퍼는 11부터 그리퍼마다 하나씩 다르게 굽는다 ([design.md](../design.md#그리퍼-교체-구조)의 자동 인식). 예비 서보는 20번대이고 버스에 두지 않으며, 갈아 끼울 때 그 관절의 ID로 바꾼다. ID는 첫 연결의 처음에 서보를 하나씩 꽂아 바꾸고(Python `set-id`, [servo-setup.md](../servo-setup.md)), 바꾼 서보에는 번호를 적어 붙인다. 바꾸기 전의 덤프는 `set-id`가 남긴다. 7개를 모두 이어 덤프와 통신 시간을 재는 것은 그 뒤다.
- 서보에 구울 값과 관절 설정은 `data/robot.toml`에 둔다: 관절마다 ID, 모델, 방향, 영점(raw), 소프트 한계, 그리고 모델마다 구울 EEPROM 값(P·I·D, 불감대, 보호 설정 등. 관절마다 다른 값은 그 관절에). 서보 각도 한계(9, 11)는 적지 않고, 영점을 잰 뒤 소프트 한계를 바깥쪽으로 반올림한 서보 값으로 계산한다 (그전에는 0~4095). 컨트롤러가 한계 밖 목표를 거르지 못해도 서보가 한 번 더 막는다. 소프트 한계가 설계 범위(`params/arm.toml`) 안인지는 테스트로 확인한다 (0009). 서보에 남은 값에 기대지 않는다: 값 적용은 쓸 수 있는 EEPROM 값(통신 속도와 ID 빼고)을 모두 맞춘다 (다른 것만 쓴다). robot.toml에 정하지 않은 것은 메모리 표의 초기값으로 맞춘다. P·I·D와 초기값이 비어 있는 칸(영향 참고)은 robot.toml에 모델별로 정한다: 게인은 P 32에서 시작해 다 만든 팔에서 재서 고르고, 튜닝하지 않는 칸(Phase, 보호·경고 조건 등)은 같은 모델끼리 첫 덤프를 견주어 정한다. 위치 오프셋(31)은 영점을 잴 때 정한 관절의 값이다 (아래 영점, 재기 전에는 0).
- 영점 (2026-11-14, 맨 서보 확인 결과로 다시 정함): 혼 톱니는 맞추지 않고 조립한다. 다 조립한 뒤 관절마다 영점 핀을 꽂고, 핀 구멍의 틈을 정한 한쪽으로 밀어 붙인 채(틈 0.05 mm가 축에서 22 mm 자리에서 ±0.07°다, [measured.toml](../../data/measured.toml)) 토크를 끄고 서보 값을 읽는다. 범위 가운데가 서보 값 2048 둘레에 오도록 위치 오프셋(31)을 계산해 EEPROM 쓰기로 굽고, 다시 읽은 핀 자리의 서보 값(`zero_raw`), 오프셋(`position_offset`), 방향을 로봇 설정에 같이 적는다. 관절 각과 서보 값 사이의 변환은 소프트웨어가 한다: 서보 값 = `zero_raw` + 방향 × (관절 각 − 핀 자리의 각) ÷ 한 칸. 핀 자리의 각(`pin_deg`)은 설계 값이다 ([0029](0029-joint-parts.md): 링크는 범위 가운데, 손목 몸통은 거기서 90° 돌린 자리).
  - 까닭: 위치 모드는 0/4095 경계를 넘지 않는다 (아래 맨 서보 확인 결과). 경계가 관절이 갈 수 있는 자리에 있으면 서보가 먼 길로 돌아 기계 멈춤을 민다. 관절 범위가 양쪽 160°이고 기계 멈춤이 163°라(J1, J2도 같다, 0029) 경계를 둘 수 있는 자리는 범위 반대편의 34°뿐이다. 오프셋으로 맞추면 경계가 그 가운데, 멈춤에서 17° 밖에 온다. 혼 톱니(25T, 한 칸 14.4°)로 맞추면 ±7.2°가 어긋나 경계가 멈춤에서 9.8°까지 다가오고, 조립할 때 서보에 전원을 넣어 정한 자리로 돌려 둔 채 혼을 끼워야 한다.
  - 경계 여유(`boundary_clearance_deg`)는 15°다: 경계가 기계 멈춤에서 12° 넘게 밖이어야 로봇 설정이 읽힌다. 영점이 들어야 할 범위는 가운데에서 ±5.0°이고, 오프셋으로 맞춘 영점은 가운데에서 한 칸(0.09°) 안이다. 그래서 이 검사는 오프셋과 영점이 어긋났는지(다른 오프셋이 구워졌는지, 핀 자리의 각을 잘못 적었는지) 본다.
  - 오프셋과 영점은 한 묶음이다. 값 적용은 로봇 설정의 오프셋을 굽고(재기 전에는 0), 로봇 설정은 영점, 방향, 오프셋을 같이 적어야 읽힌다. 서보의 오프셋이 로봇 설정과 다르면 읽는 위치가 그만큼 틀어지므로, 관절 층은 토크를 켜기 전에 오프셋을 읽어 견준다.
  - 오프셋에 대해 맨 서보 확인으로 본 것: 읽는 위치 = 엔코더 값 − 오프셋이고, 0/4095 경계도 같이 옮겨진다. 쓴 값은 4~7 ms 뒤에 새 위치로 읽힌다. 각도 한계는 읽는 위치로 듣는다 (오프셋 85인 서보로 확인했고, 한계에서 선 자리가 읽는 위치로 한계와 맞았다). 그래서 각도 한계(9, 11)는 오프셋을 구운 뒤의 서보 값으로 계산한다.
  - 영점을 재는 명령은 `zero`다 ([0034](0034-first-power-tools.md)): 방향은 핀을 꽂기 전에 관절을 + 쪽으로 돌려 재고, 틈은 늘 + 쪽(관절 각이 느는 쪽)으로 붙인다.
- 서보 보호 (2026-11-14, 맨 서보 확인 결과로 정함): 서보 스스로의 보호는 켜 둔다. 힘을 빼는 조건(19)은 첫 덤프 값 그대로 과열, 과전류, 과부하다 (STS3250은 전압도). 기준도 첫 덤프 값(보호 전류와 시간 말고는 메모리 표의 초기값과 같다)으로 둔다: 최고 온도 70°C(STS3250 80°C), 보호 전류 약 2.0 A를 2초(STS3250 2.5초), 과부하는 최대 힘의 80 %를 2초 넘으면 힘을 20 %로 줄인다. ST-3120은 오면 첫 덤프를 보고 정한다.
  - 서보 보호는 마지막 막이다. 컨트롤러가 먼저 멈춘다: 따라가기 오차와 부하가 기준을 넘은 채 오래가면 고장으로 멈춘다 ([0032](0032-run-loop.md)의 막힘과 부하).
  - 보호가 걸려도 토크 스위치는 켜진 채다 (맨 서보 확인: 과부하, 전압). 그래서 컨트롤러는 상태 바이트(65)를 늘 읽고, 비트가 하나라도 켜지면 고장으로 다룬다: 움직임을 멈추고 알린다. 과부하로 힘이 줄면 토크를 껐다 켜야 풀리므로, 다시 켜는 것은 사람이 시킬 때만 시작 절차로 한다.
  - 과부하 기준은 버티는 힘보다 한참 크다: 주 작업 영역에서 가장 무거운 J2가 정격의 0.8배로 최대 힘의 약 27 %, J3가 약 23 %다 ([0031](0031-wiring.md). 최대 힘을 멈춤 토크로 본 어림). 보호 뒤의 20 %로는 먼 자세에서 J2가 팔을 다 받치지 못할 수 있다. 다 만든 팔에서 무거운 자세로 보호에 걸리지 않는지와, 걸렸을 때 팔이 어떻게 되는지 본다.
- 움직이는 명령(토크 켜기, 목표 쓰기)은 joints만 낸다 (0009의 한곳 안전 검사). 다른 모듈이 버스에 닿지 못하게 Rust의 공개 범위로 막는다. 처음 켤 때는 토크 제한을 낮게, 속도를 느리게 둔다. 명령은 할 일을 먼저 보여 주고 `--yes`가 있어야 실물을 움직인다.
- 기록은 [0022](0022-records-and-sync.md)의 표준 경로다.
  - 실물 실행 기록: `records/<종류>/<날짜시각>_<이름>/`에 `meta.json`(조건, 코드 커밋, 서보 정보와 EEPROM 덤프, 로봇 설정), `samples.csv`(시각, raw와 변환 값), `events.csv`(알림, 표시).
  - 폰 영상: `videos/`. 두 폴더 모두 동기화 목록에 넣는다.
  - 시각은 시작부터의 초와 세계 시각을 같이 남긴다. 세계 시각은 사진·영상 시각과 맞추는 데 쓴다.
- 맨 서보 확인 프로그램(`check`, `check-state`): 짐 없는 예비 서보(ID 20번대) 하나로 시작 절차(현재 위치를 목표로 둔 뒤 토크 켜기)를 거쳐 다음을 본다. 잠금 동작, 속도 단위, 0/4095 경계를 넘는 목표, 각도 한계를 0과 0으로 둘 때(여러 바퀴), 각도 한계 밖 목표, 지금 위치가 각도 한계 밖일 때 토크 켜기, 위치 오프셋이 읽는 위치와 0/4095 경계를 옮기는지(토크를 끄고 바꾼 뒤 옛 경계 자리를 가로질러 본다), 과부하 보호에 걸릴 때 힘을 빼는지와 버티는 토크로 버티는지와 다시 풀리는 조건(힘을 빼는 조건을 켠 것과 끈 것 두 가지, 손으로 붙잡아 건다), 전압 보호(전압 하한을 10 V로 올려 가변 전원을 조금 내린다), 현재 전류의 부호. 끝나면 토크를 켠 채 두고, 프로그램을 끈 뒤, USB를 뺐다 꽂은 뒤, 서보 전원을 뺀 채, 다시 꽂은 뒤에 `check-state`로 토크 상태와 잠근 채 바꾼 값이 남았는지를 본다 (버팀은 손으로 보지 않는다. 맨 혼은 전원이 없어도 손가락으로 돌아가지 않는다). `--only`로 고른 단계만 다시 할 수 있다. 상태 묶음(레지스터 40~70)을 샘플마다 기록한다. 손으로 붙잡는 단계는 토크 5 %, 나머지는 토크 20 %로 움직인다. 어댑터를 PC에 꽂고 PC에서 돌린다 (0025). `--yes` 없이 돌리면 할 일을 보여 주고 서보 상태를 한 번 읽는다 (움직이지 않는다). Rust 버스가 실물 서보와 처음 통신하는 자리다 (첫 연결은 Python 기준 구현으로 했고, hori3 부하 시험은 가짜 서보로 했다). 순서는 [servo-setup.md](../servo-setup.md#맨-서보-확인)에 있다. 서보 온도가 높으면 팔을 쉬는 자세로 내리는 것은 joints와 실행 루프가 한다 ([0028](0028-ur-style-joints.md)).

## 근거

- 결함 두 가지(지난 값, '사용 중' 표시)는 모두 서보가 말을 안 들을 때 그것을 숨긴다. 실물을 켜기 전에 막아야 한다.
- 버스를 만지는 코드를 한 곳에 두고 움직이는 명령을 joints로만 내면, 시험 명령과 나중의 실행 루프가 같은 안전 검사를 지난다.
- 가짜 서보를 포트 자리에 끼우면 프로토콜 코드까지 시험되고, 실물 없는 PC에서 위층을 모두 만들고 시험할 수 있다 (0009의 실물 전 시험 2).
- Python 기준 구현은 공식 SDK로 같은 서보를 읽는다. 실물에서 두 구현의 결과(덤프, 동기 읽기)를 맞춰 보면 Rust 프로토콜 코드를 확인할 수 있다.

  2. 로봇 설정 파일과 읽는 코드 (J3부터). 끝났다: `data/robot.toml`(지금은 J3), `crates/controller/src/settings.rs`. 설계와 맞는지는 `tests/test_robot_settings.py`가 본다. 영점과 방향은 팔에 달고 재기 전에는 비워 두고, 비어 있는 관절은 움직이지 않는다. 확인 명령은 `cargo run -p horilab-controller -- settings`다.
  3. 서보 준비 명령: 찾기, 덤프, ID 바꾸기, 값 적용. 값 적용(`apply`, `crates/controller/src/prepare.rs`)을 먼저 만들었다 ([servo-setup.md](../servo-setup.md#값-적용)). 찾기, 덤프, ID 바꾸기는 Python 기준 구현으로 되므로 Rust로는 4~5번 뒤에 옮긴다.
  4. joints와 안전 검사. 끝났다: `crates/controller/src/joints.rs`. 토크 켜기(0009의 시작 절차와 이어받기), 한계 밖 목표 거르기, 잇단 통신 실패에 멈추기, 로봇 관절의 rad 변환, 잠근 채 바꿔 보기의 허락 범위를 가짜 서보로 시험한다.
  5. 맨 서보 확인 명령. 끝났다: `crates/controller/src/check.rs`, 기록의 `samples.csv`·`events.csv`(`record.rs`). 기록은 `records/` 아래라 동기화 목록에 이미 있다. 영점은 `zero` 명령으로 잰다 ([0034](0034-first-power-tools.md)). 게인 바꿔 보기는 팔을 조립할 때 더한다
  6. 통신 시간 재기 (0009의 실물 전 시험 3). PC와 컨트롤러 파이 모두에서 잰다
  7. [servo-setup.md](../servo-setup.md#맨-서보-확인)에 맨 서보 확인의 순서와 명령을 적는다. 끝났다
- 실물이 처음 연결되면 Python 기준 구현의 첫 연결 명령으로 서보를 찾고 덤프를 뜬다 (순서와 명령은 [servo-setup.md](../servo-setup.md)). 첫 덤프는 공장값이 아니라 SO-101에서 쓰던 상태다 (배경). 메모리 표의 초기값과 견주어 무엇이 바뀌었는지 보고(덤프 명령이 다른 칸을 보여 준다), 우리가 EEPROM을 쓰기 전으로 되돌릴 자리로 남긴다. ID는 덤프보다 먼저 하나씩 바꾸므로, 서보마다 바꾸기 전의 덤프는 `set-id` 기록에 있다. 덤프는 메모리 표 밖(71~127번)도 읽히면 같이 남긴다. 표에 없는 칸을 다른 도구가 바꿨을 수 있는데, 값 적용은 표 안의 칸만 맞추기 때문이다. 메모리 표 문서([hardware.md](../hardware.md#서보-사양))에는 초기값 칸이 있지만 P(21), D(22), Phase(18), 보호·경고 조건(19, 20), 최대 입력 전압(14), 최소 시작 토크(24), 7번은 비어 있다 (2026-11-11 확인). 새로 오는 ST-3120은 혼자 물려 아무것도 쓰기 전에 덤프를 떠서 그 모델의 공장값으로 남긴다. 이때 통신 시간도 PC와 hori3에서 잰다: 팔에 쓸 서보 7개(그리퍼 포함)를 한 버스에 다 이어, 짧은 읽기, 상태 읽기, 동기 읽기, 한 박자(동기 쓰기 + 동기 읽기)를 실행 루프처럼 10 ms마다 잰다. 짧은 읽기는 핑 대신이다 (SDK의 핑은 모델 번호를 한 번 더 읽어 왕복이 둘이다). 한 박자의 동기 쓰기는 목표 대신 토크 제한에 읽은 값을 그대로 쓴다. 각도 한계 밖에 놓인 서보에 목표를 쓰면 한계까지 움직일 수 있어서다. 목표를 6바이트(위치, 시간, 속도)로 쓰면 서보 7개에서 선로 시간이 0.28 ms 늘어난다 (셈). 응답 지연(7번)은 지금 값과 0에서 둘 다 잰다 (0은 잠근 채 써서 전원을 끄면 돌아간다). 서보 7개면 응답 지연 500 µs가 동기 읽기마다 3.5 ms라서, 100 Hz가 되는지가 여기서 갈린다. ST-3120이 오기 전에는 가진 STS3215 여섯과 STS3250으로 7개를 채운다. Python이라 어림값이고, Rust의 값은 만드는 순서 6번에서 다시 잰다.
- 실물로 확인할 것: 지금 서보들의 ID, 모델 번호, 펌웨어, EEPROM 전체, 잠금 동작(잠근 채 쓴 값이 토크를 켠 채 바로 듣는지, 전원을 끄면 사라지는지), 0/4095 경계를 넘어 움직이는지, 현재 전류(69)에 부호가 있는지, 통신이 끊기면 서보가 어떻게 하는지 (0009), ST-3120이 같은 표를 쓰는지. 잠금, 경계, 전류 부호, 끊김, 한계 밖에서 토크를 켤 때, 위치 오프셋은 맨 서보 확인으로 봤다 (아래 "맨 서보 확인 결과"). 잠금은 각도 한계를 잠근 채 바꿔 서보가 그 한계에서 서는지로 바로 듣는지를 보고, P 게인이 전원을 껐다 켠 뒤 돌아오는지로 사라지는지를 본다. 게인이 동작에 바로 듣는지는 팔에서 게인을 고를 때 본다. 현재 전류의 눈금(6.5 mA)은 짐을 든 팔에서 가변 전원 화면과 견준다.
- LeRobot 코드에 적힌 것도 실물로 확인한다 ([controller-research.md](../controller-research.md#feetech-서보를-다루는-코드)): 7번 레지스터가 응답 지연 시간인지(메모리 표에는 "예약", LeRobot은 공장값 500 µs를 0으로 바꾼다), Phase(18) 비트 4의 뜻, 어댑터의 USB 지연 타이머(FTDI는 16 ms, 이 어댑터의 칩은 모른다).
- 첫 연결 결과 (2026-11-11, PC와 hori3, 기록은 `records/servo/`):
  - 7개를 다 찾았다. 펌웨어는 모두 3.10이다. 남아 있던 ID(STS3215 1, 3, 4, 5, 6, 7, STS3250 2)를 관절 번호(1, 3, 4, 5, 6, 11, 20)로 바꿨다. 1, 4, 5, 6은 그대로 맞았다.
  - 남은 값: 응답 지연(7)은 모두 0이다 (LeRobot이 바꾸는 값). P 32, D 32, I 0이다. 위치 오프셋은 STS3215 다섯이 85이고, ID 4와 STS3250은 0이다. 각도 한계는 0~4095, 보호 전류는 310이다 (표 511).
  - 모델끼리 다른 칸: 최대·최소 입력 전압 STS3215 14.0·4.0 V, STS3250 16.0·6.0 V. 최고 온도 70·80°C. 불감대 1·0. 최소 시작 토크 16·0. 과전류 보호 시간 200·250. 보호·경고 조건 44·45와 47·45. 메모리 표 밖(71~127)은 일곱 다 읽히지 않았다.
  - 서보 전원을 5초 껐다 켜도 바꾼 ID와 모든 칸이 그대로였다. 응답 지연이 처음부터 0이라 통신 시간 재기가 바꾼 것이 없어서, 잠금 동작은 확인하지 못했다. 맨 서보 확인에서 P를 잠근 채 바꿔 보며 본다.
  - 통신 시간 (응답 지연 0, 서보 7개, Python): 한 박자는 PC에서 중간 2.36, p99 2.61, 최대 2.72 ms, hori3에서 2.75, 2.85, 2.90 ms다. 동기 읽기는 PC 2.11, 2.39, 2.46 ms, hori3 2.40, 2.55, 6.29 ms다. 선로 계산(한 박자 1.91 ms)과의 차이 0.4~0.8 ms가 USB와 운영체제 몫이다. 실패와 10 ms 넘은 것은 없다.
  - 어댑터 칩(CH343)은 Windows와 우분투 22.04가 기본 드라이버로 잡는다 (파이에서는 `cdc_acm`, `/dev/ttyACM0`). 짧은 읽기가 중간 0.5~0.64 ms라 FTDI 같은 16 ms 지연 타이머 문제는 없다.
- 맨 서보 확인 결과 (2026-11-13, PC, 예비 STS3215 ID 20, 짐 없음, 기록은 `records/servo/2026-11-13_*_check*`. 한 번 다 돌리고, 판정을 고친 단계와 손이 모자랐던 단계를 `--only`로 다시 했다):
  - Rust 버스가 실물 서보와 처음 통신했다. 응답 없음은 없었다.
  - 전원을 넣은 직후에는 목표 위치 0, 속도 0, 가속 0, 토크 한도 1000(최대)으로 읽힌다. 목표를 쓰지 않고 토크를 켜면 0으로 갈 수 있으므로, 목표를 지금 위치로 쓴 뒤 켜는 시작 절차가 꼭 필요하다.
  - 잠금: 잠근 채 쓴 P 게인(32 → 40)이 바로 읽히고, 서보 전원을 껐다 켜자 32로 돌아왔다. EEPROM은 확인을 시작할 때의 덤프와 같았다.
  - 속도 단위는 1 step/s다 (목표 속도 300에서 잰 속도와 서보가 알려 준 속도가 같다). 전원을 넣고 처음 토크를 켤 때 속도와 가속을 쓰자마자 토크를 켜자, 다음에 토크를 껐다 켤 때까지 속도 상한 없이 약 650 step/s로 돌았다. 관절 층이 상한을 쓴 뒤 20 ms 기다렸다가 토크를 켜게 고쳤고(`joints.rs`의 `CAPS_SETTLE`), 고친 뒤 전원을 넣고 처음 켜자 300 step/s로 돌았다. 원인은 짐작이라, 팔에서도 처음 움직일 때 서보가 알려 주는 속도를 본다.
  - 0/4095 경계 (각도 한계 0~4095): 3900에서 200으로 보내면 경계를 넘지 않고 가운데를 지나 먼 길로 간다. 4300은 4094에서, -200은 2에서 선다. 위치 모드는 경계를 넘지 않는다.
  - 각도 한계를 0과 0으로 두면 경계를 넘는다: 2046에서 4300으로 보내면 앞으로 약 2,250칸 돌아 203(4300 - 4096)에서 서고, -200으로 보내면 뒤로 돌아 3897에서 선다. 읽는 위치는 0~4095 안으로 돌아온다. 같은 길로 되돌아오고, 계속 돌지는 않았다.
  - 각도 한계(1500~2600) 밖 목표(3000)는 한계(2597)에서 선다.
  - 한계 밖에서 토크 켜기: 위치 2050에서 한계를 2300~2600으로 바꾸고 토크를 켜자, 0.15초 뒤부터 스스로 한계(2298)까지 움직였다 (248칸, 약 22°).
  - 위치 오프셋: 토크를 끄고 오프셋을 85에서 597로 바꾸자 읽는 위치가 512칸 내려갔다 (읽는 위치 = 엔코더 값 - 오프셋). 쓴 값은 2 ms 뒤에는 아직 옛 위치로, 4~7 ms 뒤에는 새 위치로 읽혔다. 옛 0/4095 경계 자리(3584)를 3284에서 3884로 그냥 지나갔다: 경계도 오프셋과 같이 옮겨진다.
  - 과부하 보호 (토크 한도 5 %, 기준 4 %, 0.5초, 보호 뒤 2 %로 잠깐 바꾸고 손으로 혼을 붙잡음): 힘을 빼는 조건(19)에 과부하를 켜면 0.56초에 과부하 비트가 켜지고, 토크 스위치는 켜진 채 힘이 2 %(보호 뒤 토크)로 줄었다. 혼을 놓아도 비트는 남고 서보는 움직이지 않았다 (토크를 껐다 켜서 풀었다). 과부하를 끄면 비트는 켜지지만 힘은 5 % 그대로였고, 놓자 비트가 꺼졌다. 이 판은 손이 미끄러져 혼이 목표(약 53°)까지 돌았고, 비트는 2.97초에 켜졌다.
  - 전압 보호 (전압 하한을 10.0 V로 올리고, 힘을 빼는 조건에 전압을 켬): 9.6 V에서 전압 비트가 켜지고 10.0 V에서 꺼졌다. 토크 스위치는 켜진 채였고 통신은 끊기지 않았다. 짐이 없어 힘이 줄었는지는 보지 못했다.
  - 현재 전류: 짐이 없어 값이 2~4로 작아 부호를 가리지 못했다.
  - 끊김: 프로그램을 끈 뒤와 USB를 뺐다 꽂은 뒤에는 토크가 켜진 채 목표(2048)와 잠근 채 쓴 P 게인이 그대로였다. 서보 전원을 빼면 USB가 꽂혀 있어도 서보가 응답하지 않는다. 서보 전원을 다시 넣으면 토크가 꺼져 있고, 잠근 채 쓴 값은 사라졌다.
  - 버팀은 손으로 볼 수 없었다: 맨 혼은 서보 전원이 없어도 손가락으로 돌아가지 않는다. 판정은 읽은 값으로 하고, 프로그램에서 손으로 보는 질문을 뺐다.
- 가짜 서보를 맨 서보 확인 결과(위)의 실물 동작에 맞췄다 (2026-11-14, `crates/servo/src/feetech/fake.rs`, 시험은 `crates/servo/tests/fake_servo.rs`). 실물 전 시험([0009](0009-control-architecture.md)의 2)이 가짜 서보에 기대므로, 실물과 다르면 그 시험을 믿을 수 없다.
  - 맞춘 것: 목표가 각도 한계 안으로 잘리고 0/4095 경계를 넘지 않는다 (한계가 0과 0이면 넘어 돈다). 한계 밖에서 토크를 켜면 한계까지 간다. 전원 직후의 목표는 0이다. 위치 오프셋이 읽는 위치를 옮긴다. 붙잡힌 채 과부하 보호가 걸리면 토크 스위치와 토크 한도 값은 그대로이고 힘(부하)만 보호 뒤 토크로 줄며, 토크를 껐다 켤 때까지 목표로 가지 않는다 (기록의 부하 값이 5 %에서 2 %로 줄었다). 입력 전압이 범위 밖이면 전압 비트만 켜진다.
  - 흉내 내지 않는 것: 움직이는 데 걸리는 시간, 과열과 과전류 보호(실물로 보지 않았다), 처음 토크를 켤 때 속도 상한이 먹지 않던 것(원인을 모른다).
- 관절 층은 서보 보호 비트가 켜져 있거나(보호가 걸려도 토크 스위치는 켜진 채다), 로봇 관절의 위치 오프셋이 로봇 설정과 다르면 토크를 켜지도 이어받지도 않는다 (2026-11-14, `joints.rs`의 `enable`). 로봇 설정이 EEPROM 목표(값 적용의 목표)를 주면 덤프로 모두 견주고, 하나라도 다르면 켜지 않는다: 예비 서보를 갈아 끼우고 값 적용을 빠뜨리면 각도 한계(컨트롤러 다음의 막)와 보호 설정이 다르다 (중간점검, 2026-11-14). 각도 한계와 위치 오프셋은 그 서보의 영점과 소프트 한계로 다시 계산해 견준다. 과부하로 묶인 서보는 원인을 없앤 뒤 사람이 토크를 껐다 켜서 푼다 (실행 루프의 `release` 뒤 `resume`, [0032](0032-run-loop.md)).
- Python 기준 구현은 첫 연결 명령(찾기, 덤프, 통신 시간, ID 바꾸기)을 Rust로 옮긴 뒤 지운다 (Rust 버스는 맨 서보 확인에서 실물과 통신했다). 그전에 SDK를 올리면 `typings/scservo_sdk`와 테스트로 다시 확인한다.
