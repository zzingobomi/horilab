# 0023. 로봇 컨트롤러와 응용의 경계

- 상태: 제안
- 날짜: 2026-11-10

리서치 뒤에 검토한 대안, 결정, 근거, 영향을 채우고 채택으로 바꾼다. 아래는 리서치 전에 정리한 방향과 정할 것이다.

## 배경

- 첫 대표 작업은 미니 팔레타이징이지만 팔레타이징만 하는 로봇이 아니다. 물건 집기, 용접 흉내처럼 여러 작업에 쓴다 ([goals.md](../goals.md)의 6축 확인 작업과 도구 교체도 같은 방향이다).
- 지금 정해진 제어 구조([0009](0009-control-architecture.md))는 상위 제어가 시간이 붙은 관절 궤적을 모터 프로세스에 보내는 데까지다. 여러 작업에서 실물 로봇을 어떻게 제어할지, 어디까지가 로봇이고 어디부터가 작업인지는 정하지 않았다.

## 제안하는 방향

산업용 로봇처럼 로봇 컨트롤러와 응용을 나눈다.

```
[응용]  팔레타이징 | 물건 집기 | 용접 흉내 | …
   작업 순서, 비전, 작업 공간 지식 (팔레트 위치 등)
        │ 이동 명령 ↓   ↑ 상태, 이벤트
═══════════════ 컨트롤러 API ═══════════════
[로봇 컨트롤러]  어떤 응용에도 종속되지 않는다
   명령 대기열 → 경로 계획 (IK, 보간, 블렌드, 시간 매기기) → 관절 궤적
     → 실행 루프 + 안전 검사 (0009) → 실물 서보 | 시뮬레이션
   도구 (끝점 위치, 그리퍼), 보정, 상태 내보내기, 기록 (0022)
[펜던트]  게임패드, 폰 브라우저 화면 → 컨트롤러에 붙는 손님
```

- 컨트롤러는 계속 도는 서비스이고 API를 준다: 이동 명령(관절 이동, 직선 이동, 원호 이동 등에 속도와 블렌드 값), 정지, 관리 명령(토크 켜기·끄기, 실물·시뮬레이션 전환), 상태 스트림, 이벤트(동작 끝남, 거부됨, 오류). UR의 URScript, RTDE, Dashboard Server에 해당한다.
- 블렌드(연속된 이동 명령 사이의 모서리를 둥글게 이어 멈추지 않고 지나가는 것)는 컨트롤러가 한다. 다음 명령을 미리 알아야 모서리를 이을 수 있고, 관절 한계와 IK는 로봇이 알기 때문이다. 산업용 컨트롤러도 그렇다 (UR의 블렌드 반지름, ABB의 zone). 그래서 응용은 궤적이 아니라 이동 명령을 보낸다.
- 경계는 둘이 된다: 응용 ↔ 컨트롤러(이동 명령)와, 컨트롤러 안의 경로 계획 ↔ 실행 루프(관절 궤적, 0009). 0009를 뒤집지 않고 그 위에 한 층을 더한다.
- 비전과 작업 순서는 응용이 한다.
- 컨트롤러를 시뮬레이션으로 띄우면 응용은 실물과 같은 API로 붙는다 (UR의 URSim처럼). 실물이 없는 PC에서 응용을 개발한다 ([0022](0022-records-and-sync.md)).
- 펜던트는 둘이다.
  - 게임패드: 조그. 트리거를 데드맨으로 쓴다.
  - 폰: 브라우저로 컨트롤러의 웹 화면에 들어간다 (앱을 설치하지 않는다). 상태, 저장한 자세, 프로그램 실행·정지, 카메라 화면, 화면 조그. PC 브라우저도 같은 화면을 쓴다. 계획해 둔 3D 화면([software.md](../software.md#패키지)의 React(R3F))과 합친다.
- 펜던트에는 실제 비상정지 버튼과 데드맨 스위치가 없으므로 이렇게 막는다.
  - 누르고 있을 때만 움직이고, 손을 떼거나 터치가 취소되면(전화, 알림 등) 멈춘다.
  - 명령이 끊기면(와이파이, 화면 꺼짐, 탭 전환) 컨트롤러가 멈춘다. 조그를 짧은 궤적으로 보내는 0009의 방식이 이를 받쳐 준다.
  - 화면의 정지는 소프트웨어 정지다. 최종 수단은 가변 전원 차단이다 ([hardware.md](../hardware.md#안전)).
  - 조종권은 한 번에 하나(폰, 게임패드, 응용 중)만 갖고, 명시적으로 넘겨받는다.
  - 웹 화면은 집 랜 안에서만 연다.
- 로봇보다 컨트롤러가 먼저 커지지 않게 한다. 경계와 큰 구조는 먼저 정하고, 기능은 실제 응용이 필요할 때 더한다. API가 바뀌어도 응용은 클라이언트 라이브러리 한 곳만 고치게 한다.

## 하드웨어가 정하는 한계

서보가 위치 제어 서보라서 산업용 컨트롤러의 기능이 다 되지는 않는다.

| 기능 | 이 로봇 |
|---|---|
| 관절 이동, 직선 이동, 조그, 속도 조절, 한계, 정지, 상태 내보내기, 시뮬레이터 | 된다 |
| 블렌드 | 된다. 다만 직교 경로의 모서리 잇기, 시간 매기기, IK 잇기가 가장 공이 드는 부분이다. 산업용처럼 일정한 속도까지는 어렵고, 보기에 매끄러운 수준을 노린다 |
| 부딪히면 멈추기 | 어림만 된다. 서보가 읽는 부하로 큰 충돌 정도만 잡는다 |
| 손으로 끌어서 티칭 | 어렵다. 토크를 끄면 팔이 떨어진다 |
| 힘 제어, 안전 인증 수준의 정지 | 안 된다 |
| 실시간 보장 | 모터 프로세스는 로봇 옆 컨트롤러 파이에서 Rust로 돈다 ([0025](0025-controller-on-pi.md)). 리눅스라 실시간 커널을 쓸 수 있다. 개발할 때 PC(Windows)에서 돌리면 보장이 없다 |

## 정할 것

아래 추천은 리서치([controller-research.md](../controller-research.md))를 바탕으로 했다. 사용자와 정한 뒤 이 기록을 채택으로 바꾸고 0009를 조정한다.

1. **경계.** 무엇이 컨트롤러이고 무엇이 응용인가.
   - 추천: 컨트롤러가 IK, 이동 명령과 블렌드, 시간 매기기, 한계, 안전 검사, 정지와 복구, 조종권과 모드, 조그, 웨이포인트·프로그램 저장과 재생을 맡는다. 공구 끝점(TCP), 짐 무게, 이름 붙은 좌표계도 컨트롤러에 저장하고, 로봇 모델(URDF·MJCF)도 컨트롤러가 내준다. 응용은 작업 순서, 비전, 팔레트 배치, 좌표계를 재서 구하는 일을 맡는다. 산업용(UR, ABB)과, 로봇 옆에 컨트롤러를 둔 데스크톱 팔(xArm, Reachy, PAROL6 서버)이 모두 이렇게 나눈다.
   - 애매한 것: 장애물을 피하는 경로 계획은 응용에 두고, 컨트롤러는 한계와 자기 충돌만 본다. 손목 D405의 핸드아이 값은 로봇과 카메라 받침에 매인 값이라 로봇 설정(`data/`)에 두고 컨트롤러가 내준다 (조사한 곳들은 이 문제를 다루지 않았다). 카메라는 컨트롤러가 아니라 카메라 파이의 서비스로 둔다.
2. **API.** 명령, 상태, 이벤트의 목록과 주고받는 방식. 처음에는 실제 응용이 쓰는 것만 둔다.
   - 명령은 바로 결과를 돌려준다: 성공, 조종권 없음, 상태가 맞지 않음, 값이 틀림, 그 밖 (UR 제어 API의 0, -1, -2, -100과 같은 나눔).
   - 명령 묶음:
     | 묶음 | 명령 |
     |---|---|
     | 조종권 | 받기, 돌려주기 |
     | 토크 | 켜기(그 자리에서 버팀), 끄기 |
     | 복구 | 보호 정지 풀기(이유 확인), 고장 지우기 |
     | 이동 | 관절 이동, 직선 이동(원호는 나중). id를 붙여 줄 세우고 줄 길이에 제한을 둔다 |
     | 흐름 | 멈춤, 이어서, 정지, 줄 비우기 |
     | 속도 | 속도 비율 |
     | 조그 | 흐름(수명이 지나면 멈춤), 한 스텝 |
     | 티칭 | 웨이포인트·프로그램 저장, 불러오기, 재생 |
   - 블렌드 규칙: 블렌드가 겹치면 반지름을 줄이고 건너뛰지 않는다 (UR 모션 버전 2). 블렌드 구역에 들어설 때 다음 이동이 없으면 그 점에서 정확히 멈추고 경고를 낸다 (ABB).
   - 상태 흐름: 실행 루프 주기로 내고, 클라이언트마다 솎는 비율을 고른다 (UR RTDE). 폰 화면은 20~30 Hz면 된다. 항목은 시각, 순번, 로봇 상태(끊김, 토크 꺼짐, 대기, 동작), 안전 상태(정상, 보호 정지, 고장), 프로그램 상태와 지금 이동 id, 줄 길이, 조종권 주인과 모드, 속도 비율(설정 값과 실제 값), 목표·실제 관절 각, 공구 끝점 자세, 서보마다 온도·부하·전압·오류 비트, 백엔드(실물, 시뮬레이션), 프로토콜 판이다.
   - 이벤트는 순번을 붙여 바로 민다: 이동 끝남·실패·취소, 블렌드 조정, 보호 정지(이유, 관절, 코드), 조종권·모드 바뀜, 흐름 시간 넘김.
   - 움직임 종류는 둘로 시작한다: 줄 세운 이동(블렌드)과 최신 목표만 따르는 흐름(조그). 지금 상태에서 다시 계획하는 이동과 서보 흐름(시각 서보)은 필요할 때 더한다.
3. **조종권 규칙과 펜던트 모드.**
   - 추천: 한 번에 하나만 조종하고, 상태 보기는 누구나 한다. 로봇 옆 펜던트는 언제든 조종권을 가져간다. 원격 응용은 명시적으로 받고 돌려준다. 오류나 보호 정지가 나면 조종권이 컨트롤러로 돌아가고 다시 받아야 한다 (FANUC). 조종하던 연결이 끊기면 조종권이 풀리고 감속해 버틴다.
   - 조종권 규칙은 모터 프로세스가 모든 명령 길에서 지킨다. Reachy Mini처럼 우회되는 잠금은 막지 못한다.
   - 수동 모드(펜던트)는 누르는 동안만 움직이고 속도 상한을 둔다. 상한은 산업용의 250 mm/s보다 낮게, 관절 시험과 팔 시험으로 정한다.
   - 남은 질문: 무엇을 "로봇 옆"으로 볼지(파이에 꽂은 게임패드만인가, 폰도인가), 열쇠 스위치 없이 모드를 어떻게 바꿀지, 랜 안에서도 조종권을 받을 때 PIN 같은 인증을 둘지.
4. **전송 방식과 응용용 클라이언트 라이브러리.**
   - 추천 (리서치의 설계 A): 컨트롤러가 펜던트 화면(HTTPS)과 WSS API 하나를 직접 연다. 브라우저, Python 응용, 게임패드 프로그램이 모두 여기에 붙는다. 메시지는 JSON(`{type, id, seq, t, body}`)으로 시작한다.
   - 데드맨은 누르는 동안 보내는 메시지를 컨트롤러가 직접 잰다. 어느 전송 방식의 연결 확인도 그만큼 빠르지 않다.
   - 들고 나는 메시지는 컨트롤러가 MCAP로 기록한다. 늘 기록할지 필요할 때만 할지(파이 SD 카드 마모)와 [0022](0022-records-and-sync.md)의 동기화에 잇는 법은 [0026](0026-pi-runtime-deploy-records.md)에서 정했다: 늘 켜 두는 기록은 메모리 링 버퍼에만 두고 보호 정지·오류 때 파일로 남기며, 시험 기록은 세션 파일로 파이가 드라이브에 올린다.
   - Python 클라이언트 라이브러리는 실물 컨트롤러와 PC 시뮬레이션 컨트롤러에 같게 붙는다.
   - Zenoh는 여러 기계가 서로 얽힐 때 컨트롤러 안쪽에 더한다 (리서치의 설계 B). 0009에 적혀 있던 pyzmq는 모터 메시지에는 쓰지 않고, 카메라 파이에서 PC로 가는 영상에는 그대로 둔다 ([0008](0008-environment-and-packages.md)).
   - 사용자가 정할 것: 폰 펜던트의 HTTPS 방식. 사설 인증 기관(기기마다 인증서 설치)이나 도메인 + Let's Encrypt(기기 설정이 없음)다. 둘 다 돈이 들지 않는다. 사용자가 AWS Route 53에 가진 도메인이 있어서, Let's Encrypt 인증서를 DNS-01로 받을 수 있다. NAS의 DSM 내장 Let's Encrypt는 사용자 도메인에 HTTP-01만 지원해 이중 NAT인 집에서는 안 되므로 따로 받는다 ([controller-research.md](../controller-research.md#6-nas-쓸-자리)). 쓰는 폰의 OS와 브라우저에 따라 갈린다.
5. **컨트롤러 자리.** [0025](0025-controller-on-pi.md)에서 정했다: 로봇 옆 컨트롤러 파이이고, PC 없이도 쓴다. 응용을 어디에 둘지는, 응용이 늘고 API가 자리 잡을 때까지 같은 레포에 두기를 추천한다.
6. **실물이 없는 PC에서 실물을 어디까지 다룰지.** 추천은 그대로다: 시뮬레이션, 기록 분석, 실물 상태 보기까지이고, 사람이 가변 전원 옆에 없을 때는 실물을 움직이지 않는다. 조종권 규칙으로 막을 수 있다. 원격 응용이 조종권을 받으려면 로봇 옆 펜던트에서 정해진 시간 안에 허락하게 한다 (ABB의 RMMP).
7. **브레이크가 없는 팔의 정지.** 산업용의 Cat 0·1(전원 차단)은 브레이크가 팔을 잡는다는 전제라, 이 팔에서는 팔이 떨어진다.
   - 추천: 보호 정지와 소프트웨어 정지는 감속해 토크를 켠 채 버틴다. 산업용 Cat 2에 해당하고, 0009와 같다. 토크를 끄는 것은 사람이 명시적으로 할 때와 서보 자체 보호가 끊을 때뿐이다. 최종 수단은 그대로 가변 전원 차단이다 ([hardware.md](../hardware.md#안전)).
8. **게임패드를 어디에 꽂나.**
   - 추천: 컨트롤러 파이. 데드맨이 와이파이를 건너지 않고, PC 없이 쓸 때도 된다. 컨트롤러 프로세스가 직접 읽는다. gilrs는 리눅스에서 C 라이브러리(libudev)가 필요해 정적 빌드([0026](0026-pi-runtime-deploy-records.md))와 부딪히므로, 순수 Rust인 evdev를 같이 따진다.

## 리서치 계획

2026-11-10에 모두 조사했다 ([controller-research.md](../controller-research.md)). 산업용 컨트롤러, 데스크톱·오픈소스 팔, 전송 방식, 시뮬레이션 연결과 파이용 계획 라이브러리(1~4절)에 이어, 실물이 있는 PC에서 파이, NAS, PC, 집 네트워크를 확인한 뒤 파이 컨트롤러의 실행 환경·빌드·배포·기록(5절)과 NAS 쓸 자리(6절)를 조사했다. 그 추천은 검토를 거쳐 [0026](0026-pi-runtime-deploy-records.md)으로 정했다.

구현할 때 한다.

- 블렌드와 경로 시간 매기기 도구 고르기 (후보와 라이선스는 리서치에 있다)
- 직교 경로를 따라 IK를 끊김 없이 잇는 방법, 특이점 처리
- 브라우저 펜던트 세부 (터치 처리, 화면 켜 두기)

위 안전 원칙은 따져서 나온 것이라 리서치하지 않는다. 서보 연결 프로그램의 맨 아래층(서보 ID, EEPROM 읽기·쓰기, 상태 읽기)은 경계와 상관없이 필요해서, 리서치를 기다리지 않고 시작해도 된다 (Rust, [0024](0024-servo-bus.md), [0025](0025-controller-on-pi.md)).
